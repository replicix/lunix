### Changed

- **Map bytes counter.** `EngineStats::map_bytes_written` (`lunix-iface`): cumulative bytes of the map packs sealed by
  commits (C5, the sum the engine already settles in the space ledger). Kept by the engine, stored in a new checkpoint stats
  slot (`EngineStats::SLOTS` 24 to 25, appended before `stage_ns`), restored on open like the other counters, and part of
  `lunix status --json` under `stats`. The checkpoint's stats meaning is "defined by lunix-engine, not frozen"
  (on-disk-formats, `n_stats` up to 192), so no format change. Test:
  `map_bytes_written_grows_per_commit_and_survives_a_reopen` (both chunk sizes).
  `bench/phase1/chunksize/analyze.py` now computes map seal write amplification exactly (delta of the counter over bytes
  written) and labels a cell "proxy" only when the input lacks the counter; `selftest.sh` checks both cases.
- **Worker count key.** The "workers" of the plan's seqw cell are the destage pool's worker threads (hash, dedup, compress,
  seal) per attached volume. New `lunixd.toml` key `destage_workers`: integer 1 to 64, 0 and above 64 refused; default
  unset = the pool's own `max(2, cpus / 2)` (cpus as seen by the daemon's affinity). Documented in the table of
  `crates/lunixd/src/config.rs` (the README of lunixd is already past the 40 line ownership limit, and there is no config reference under `docs/reference` yet).
  Test: `destage_workers_defaults_to_the_pool_and_is_bounded`. `tests/perf/partA.sh` sets it through `CFG_EXTRA` from
  `DESTAGE_WORKERS` (default 8, `default` = leave unset); it is a daemon setting, so it holds for every cell of the run and is
  recorded per cell (`destage_workers`) and in the results header.
- **Chroot `/dev`:** the read-only rbind stays; `chunksize.sh` carries a comment naming it as the one exception to
  CONVENTIONS rule 3 (accepted by the lead 2026-11-18). CONVENTIONS.md untouched.
- **GC (Q7):** harness calls `lunix gc NAME --json` (matches the CLI: `--json`, `--status`, `--dry-run`; the call runs a pass to
  its end). Added `gc_idle`, polling `lunix gc NAME --status --json` until `.state == null`, after each pass.
- **Counters (Q8):** checked against main: `stats.{bytes_written,ops_write,cold_rmw}` and `space.map` (status body),
  `journal_used` (top level of the status body), fsck `ratios.{mapped_chunks,dedup_ratio,compression_ratio,unique_clen,
  bytes.{segments,map_packs,commits,index}}`: all exist, no rename needed.
- **Read cache (Q3):** default left; each Part A cell records `read_cache_max` (from `volume.json`), `cache_bytes_end`
  (`space.cache`) and `map_bytes_written_end`. There is no cache hit counter in the status on main.
- **Ownership:** the paths above and the prep report name added to `[m16]` in `tools/ownership.toml`.

**Shortfall analysis** (ceilings from `bench/BASELINE.md` are printed per row in `partA-tables.md`):

1. **r4k: the row does not measure cache hits at the plan's cell.** The 4 GiB working set against the default 128 MiB cache sends
   every read to the store: the profile (`perf` of the daemon, first repetition) is `_blake3_hash_many_avx512`, `ZSTD_decompressSequences`,
   `memmove` and `ChunkCache::insert` on the four `lunix-read-N` threads, each busy 27.8 s of the 30 s window (0.90-0.93 of a core;
   `partA-tables.md`), the queue threads 26.6 s. The read pool is the saturated resource; 8 queues do not help at 64 KiB (259,806).
   Supplementary run with `read_cache_max` = 8 GiB (the working set resident; `partA-readcache-tables.md`, 3 repetitions):
   r4k reaches **831,952 IOPS at 64 KiB and 771,691 at 16 KiB with 8 queues** (373,047 / 353,272 at 4 queues), the store reads vanish
   (4.3 us of daemon CPU per I/O against 22-25 us). So the cache size accounts for 100 % of the IOPS gap (explained =
   (target - ceiling)/(target - measured) is clamped to 1). **The p99 target is not reachable at the cell as specified**: eight jobs
   at queue depth 128 keep 1,024 requests in flight, so by Little's law the mean latency at 500 K IOPS is 2.0 ms against a 150 us p99
   target; measured p99 is 4.9 ms at 832 K IOPS (mean about 1.2 ms). The row's IOPS and p99 targets describe different load
   points; the lead should decide whether the cell should use a shallower queue for the latency target.
2. **w4k and seqw: the engine's write path, with the host's storage a small part.** The journal's file system is on a network
   block volume with the raw limits measured in this session (`raw/fio-journal-raw.json`): 4k random write 2,732 IOPS (p50 363 ms),
   64 KiB writes with `fdatasync` 263 commits/s (16.9 MB/s), 4 KiB with `fdatasync` 254/s (a second volume of the host measured
   3,000, 343 and 371/s, so the limit is not specific to that mount); null_blk in the same session 1.44 M IOPS at 4k write
   and 11.8 GB/s at 1M. The measured 2,890-3,762 IOPS and 0.04 GB/s sit at these raw limits and the daemon is mostly idle (queue
   threads 0.2-0.6 s of CPU per window), which suggests a disk-bound row; the RAM-backed reference shows it is not only that. The
   same cells on a RAM-backed ext4 volume directory (supplementary `partA-ramref-tables.md`: journal and store not disk-bound; 2 GiB
   working set, 16 GiB volume, 3 repetitions) give w4k **6,063 IOPS at 64 KiB (4 q) and 12,980 at 16 KiB (8 q)** and seqw **0.39 / 0.32 GB/s**
   (2-4 % of the targets), queue threads still idle (1.2-2.2 s of CPU per window), fio p99 0.7-1.2 s. Fractions of the gap: the storage
   explains (6,063 - 3,762) / (300,000 - 3,762) = 0.8 % of the w4k gap at 64 KiB (3.4 % at 16 KiB: (12,980 - 2,890) / (300,000 - 2,890)) and
   (0.39 - 0.04) / (3.0 - 0.04) = 12 % of the seqw gap; **88-99 % is the engine**: the write path is limited below the queue threads by
   the destage/space side. `perf` of the 64 KiB 4-queue cells on the RAM volume (`partA-ramref-perf/`, first repetition) shows the
   `lunix-space` thread running 11.5 s of its window with `crc32c`, `memcmp`, SHA-256, `LsmIndex::get` and `lunix_gc::mark::Mark::unit`
   on top (w4k), and BLAKE3, `memset`, `Bloom::maybe_contains` and `Run::lookup` (seqw): garbage-collection marking and index
   lookups run on the thread that accounts space while the journal is full (journal use 0.27-0.67 GB of 1 GiB at the end of the
   disk-backed cells), and `cold_rmw` is about 80 % of the writes in the Part B workloads. This needs an owner (destage/space thread,
   GC concurrency with ingest); nothing here is tuned.
3. **seqr: at 16 KiB with the default cache the target is missed by 20 %** (3.98 GB/s at 8 queues, 3.88 at 4): daemon CPU 1,025 us per
   1 MiB read (64 chunk lookups, BLAKE3, insert, against 16 at 64 KiB: 586 us), the read workers 20 s of 30 s per thread, the
   queue threads 6-12 s. With the cache holding the working set seqr passes at both sizes (9.61 GB/s at 16 KiB, 11.60 GB/s at
   64 KiB, 8 queues). 64 KiB meets the row in both configurations.

### Part B: ADR-5

Workloads (each chunk size back to back; `randmix` 30 min, `seqrand` 16 GiB fill plus 15 min overwrite, `pgbench` scale 1000,
`-c 16 -j 4 -T 1800`, ext4 and xfs, `vm` the three raw images churned in chroots), all once: **noise caveat on every number**.
Tables: `bench/phase1/chunksize/RESULTS.md`. Aggregate over VM-image and pgbench:

| clause | 16 KiB | 64 KiB | holds |
|---|---|---|---|
| 1. stored bytes (data + map) per logical GiB written >= 15 % lower at 16 KiB | 0.0682 | 0.0590 | **no**: 16 KiB is 15.6 % higher (pgbench ext4 +18 %, xfs +30 %, vm +6.8 %) |
| 2. daemon CPU per GiB <= 1.3x | 6.062 s/GiB | 4.441 s/GiB | **no**: 1.36x (pgbench alone 1.05x; the VM cell 10.43 against 3.95 s/GiB) |
| 3. Part A rows that pass at 64 KiB still pass at 16 KiB | seqr 3.98 GB/s | seqr 8.42 GB/s | **no** (with the working set resident in the cache seqr passes at both sizes and the clause would hold) |

**Recommendation by the rule: 64 KiB** (both sizes stay supported per volume). The proposed Gate outcome block is in
`bench/phase1/chunksize/RESULTS.md`. The map at 16 KiB is 7x larger per TiB mapped (11-13 GiB/TiB against 1.7) and the compression and
dedup gains of the smaller chunk (VM dedup 1.067 against 1.045, compression 2.87 against 3.00 on the VM images, 12.8 against 13.3 on
pgbench) do not pay for it; 16 KiB wins on the fio write latency (randmix p99 10.7 against 33.8 ms) and on GC pressure (peak store
27.8 against 69.1 GiB under random overwrite) and loses 16-18 % of pgbench TPS (756/738 against 905/898; PostgreSQL p99 34.8/35.5 ms
against 42.0/38.3 ms).

**Finding for the lead: GC falls behind under sustained random overwrite.** The 64 KiB randmix cell grew the store to 69.1 GiB
for 10.2 GiB of live data (linear, 2.3 GiB per minute, collector in `compacting`), 52.4 GiB for seqrand; 16 KiB 27.8 and 25.7 GiB;
after the three final passes 11-16 GiB. Store-over-time and GC state per cell are in the committed `store-timeline.tsv` files; the
harness guard (90 GiB) did not trigger and the 100 GiB cap was respected.

### Deviations and what was changed in the harness

1. **Tooling that was changed for the runs** (all under `tests/perf/` and `bench/phase1/chunksize/`): PostgreSQL binaries found in
   `/usr/bin` when `/usr/lib/postgresql/*/bin` does not exist; a store-over-time sampler (every 60 s: store bytes, journal use, map
   bytes, bytes written, GC state) and a 90 GiB cap guard in `chunksize.sh`; `partA.sh` knobs `READ_CACHE_BYTES` and `SKIP_WRITE_CELLS`
   for the supplementary run; the VM workload rewritten: the chroot part is a new script `tests/perf/vm-chroot.sh` run in a **private mount
   namespace** (`unshare --mount --propagation private`), the loop device's partition is awaited (udev race), the image copy is grown by
   6 GiB (`truncate`, `growpart`, `e2fsck`, `resize2fs`: the images' root file systems of 2.1-2.9 GiB filled up under the upgrade), the image's
   dangling `resolv.conf` link is replaced, and the package install falls back to one package at a time when the bulk install hits
   conflicts (74/64/0 names skipped on the three images; 1918/1764/1905 packages installed per image at both sizes);
   `analyze.py` labelled "lower" a value that was higher (fixed: the sign is now in the word).
2. **Incidents.** (a) My remote-command shim re-launched the first Part A run (a failed tunnel return was retried), the second copy waited for the
   lock and wiped the first run's output directory at the end; the first run's per-cell summary lines were kept (`p1-m16` scratch only) and agree with the
   rerun, and the rerun is the committed one (the shim is now idempotent). Killing the duplicate left one orphan fio and a ublk device, removed with
   `lunix-ublk-testd del --force` (the device was this run's, its daemon gone). (b) The first two VM attempts failed in the harness (partitions not yet
   visible; then `umount` of a read-only recursive bind of `/dev` that is `shared` on this host): the mounts propagated into the mount namespaces
   of `systemd-udevd`, `dbus-broker`, `NetworkManager`, `systemd-userdbd`, `systemd-resolved` and `systemd-oomd`, which kept the loop devices busy.
   Cleaning needed `nsenter` unmounts and a **restart of `systemd-userdbd`, `systemd-resolved` and `systemd-oomd`** (the mounts were not
   reachable by path in their namespaces), and a restart of `lunixd` with the same config to let a hung unmount finish (ext4 on a ublk device
   whose daemon had exited). Everything was verified clean afterwards (`ublk-leftovers`: clean, no loop devices, no mounts). The private
   mount namespace in `vm-chroot.sh` is the fix. (c) The CI on the host was run in pieces (no-fail-fast copy of `ci.sh` made on the host,
   not committed) after a dropped tunnel.
3. **Supplementary runs outside the plan** (declared as such, committed separately): Part A with `read_cache_max` 8 GiB, and Part A on a

5. **CONVENTIONS rule 3 exception** (chroot `/dev`, rbind read-only) unchanged and accepted on 2026-11-18; it now lives in a private mount
