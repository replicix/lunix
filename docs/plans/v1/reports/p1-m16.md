**Shortfall analysis** (ceilings from `bench/BASELINE.md` are printed per row in `partA-tables.md`):

1. **r4k: the row does not measure cache hits at the plan's cell.** The 4 GiB working set against the default 128 MiB cache sends
   every read to the store: the profile (`perf` of the daemon, first repetition) is `_blake3_hash_many_avx512`, `ZSTD_decompressSequences`,
   `memmove` and `ChunkCache::insert` on the four `lunix-read-N` threads, each busy 27.8 s of the 30 s window (0.90-0.93 of a core;
   `partA-tables.md`), the queue threads 26.6 s. The read pool is the saturated resource; 8 queues do not help at 64 KiB (259,806).
   Supplementary run with `read_cache_max` = 8 GiB (the working set resident; `partA-readcache-tables.md`, 3 repetitions):
   r4k reaches **831,952 IOPS at 64 KiB and 771,691 at 16 KiB with 8 queues** (373,047 / 353,272 at 4 queues), the store reads vanish
   (4.3 us of daemon CPU per I/O against 22-25 us). So the cache size accounts for 100 % of the IOPS gap (explained =
   (target - ceiling)/(target - measured) is clamped to 1). **The p99 target is not reachable at the cell as specified**: eight jobs
   at queue depth 128 keep 1,024 requests in flight, so by Little's law the mean latency at 500 K IOPS is 2.0 ms against a 150 us p99
   target; measured p99 is 4.9 ms at 832 K IOPS (mean about 1.2 ms). The row's IOPS and p99 targets describe different load
   points; the lead should decide whether the cell should use a shallower queue for the latency target.
2. **w4k and seqw: the engine's write path, with the host's storage a small part.** The journal's file system is on a network
   block volume with the raw limits measured in this session (`raw/fio-journal-raw.json`): 4k random write 2,732 IOPS (p50 363 ms),
   64 KiB writes with `fdatasync` 263 commits/s (16.9 MB/s), 4 KiB with `fdatasync` 254/s (a second volume of the host measured
   3,000, 343 and 371/s, so the limit is not specific to that mount); null_blk in the same session 1.44 M IOPS at 4k write
   and 11.8 GB/s at 1M. The measured 2,890-3,762 IOPS and 0.04 GB/s sit at these raw limits and the daemon is mostly idle (queue
   threads 0.2-0.6 s of CPU per window), which suggests a disk-bound row; the RAM-backed reference shows it is not only that. The
   same cells on a RAM-backed ext4 volume directory (supplementary `partA-ramref-tables.md`: journal and store not disk-bound; 2 GiB
   working set, 16 GiB volume, 3 repetitions) give w4k **6,063 IOPS at 64 KiB (4 q) and 12,980 at 16 KiB (8 q)** and seqw **0.39 / 0.32 GB/s**
   (2-4 % of the targets), queue threads still idle (1.2-2.2 s of CPU per window), fio p99 0.7-1.2 s. Fractions of the gap: the storage
   explains (6,063 - 3,762) / (300,000 - 3,762) = 0.8 % of the w4k gap at 64 KiB (3.4 % at 16 KiB: (12,980 - 2,890) / (300,000 - 2,890)) and
   (0.39 - 0.04) / (3.0 - 0.04) = 12 % of the seqw gap; **88-99 % is the engine**: the write path is limited below the queue threads by
   the destage/space side. `perf` of the 64 KiB 4-queue cells on the RAM volume (`partA-ramref-perf/`, first repetition) shows the
   `lunix-space` thread running 11.5 s of its window with `crc32c`, `memcmp`, SHA-256, `LsmIndex::get` and `lunix_gc::mark::Mark::unit`
   on top (w4k), and BLAKE3, `memset`, `Bloom::maybe_contains` and `Run::lookup` (seqw): garbage-collection marking and index
   lookups run on the thread that accounts space while the journal is full (journal use 0.27-0.67 GB of 1 GiB at the end of the
   disk-backed cells), and `cold_rmw` is about 80 % of the writes in the Part B workloads. This needs an owner (destage/space thread,
   GC concurrency with ingest); nothing here is tuned.
3. **seqr: at 16 KiB with the default cache the target is missed by 20 %** (3.98 GB/s at 8 queues, 3.88 at 4): daemon CPU 1,025 us per
   1 MiB read (64 chunk lookups, BLAKE3, insert, against 16 at 64 KiB: 586 us), the read workers 20 s of 30 s per thread, the
   queue threads 6-12 s. With the cache holding the working set seqr passes at both sizes (9.61 GB/s at 16 KiB, 11.60 GB/s at
   64 KiB, 8 queues). 64 KiB meets the row in both configurations.

### Where the write time goes

Evidence from the stall profile (64 KiB, 4 queues, 8 destage workers):

1. **The destage workers are blocked reading the journal back, one piece at a time.** Kernel stacks of the daemon's uninterruptible threads
   (`dstacks.txt`, 276 samples in w4k): 250 are `lunix-coord` in `pread64 -> btrfs_direct_read -> iomap_dio_rw`; seqw 147 of 180. The off-CPU
   `perf` (`offcpu-report.txt`) puts 82.8 % of all blocked time of the daemon in `__iomap_dio_rw` under `lunix_journal::sys::read_aligned`
   (an `O_DIRECT` `pread` of the journal ring file), 2.6 % in `fdatasync` under `lunix_store::container::ContainerWriter::seal`. On-CPU
   the daemon is nearly idle (4.1 CPU-seconds in a 20 s window, top symbol `ZSTD_compressBlock_fast` in `lunix-coord`). A direct read with
   about 3 ms of latency on this host's volume, eight workers one read at a time: 8 / 3 ms is about 2.7 K pieces per second, which is the measured
   write rate (2.4-2.9 K IOPS for 4 KiB pieces); seqw reads 64 KiB pieces and lands at 0.04 GB/s for the same reason.
2. **The 15-35 s completion stalls are journal-ring waits that end only at commit.** fio's latency for a w4k cell: p50 9.5 ms, p99 17.1 s,
   max 35.4 s (bimodal). `journal_used` sits at 512 MiB in every sample (the ring is full: new writes park in `queue.rs` at the
   `try_reserve` -> `Full` branch with `ring_wait` set and `journal_full` raised) and the ring is released only at commit step C9
   (`coord.rs`, `journal_full.store(false)` after `reclaim`). A commit destages the whole cut, so its length is cut size / (2.4 K pieces/s):
   `stats.commits` grew 31 -> 32 -> 33 at t = 9, 30, 58 s (one per 22-28 s), and a parked write waits for the next one. The collector is not it
   (`gc.state` null during w4k; during seqw it is `condemning` but the commit cadence is the same, 41 -> 44 commits in 36 s), the **paced band
   is not engaged** (`throttle.state` open, `paced_waiters`, `space_waiters`, `delayed_writes`, `delay_max_ms`, `throttled_ms`, `enospc`
   all 0 in every sample, `gc_pressure` normal), and the space limit is far (used 5.2 GB of 68.7 GB). No counter exposes ring-full parking;
   the cause above is inferred from the pinned `journal_used`, the commit cadence and the latency distribution. The control path stalls too:
   `lunix status` and `lunix gc --status` each took 10-15 s during the cells (the 5 s sampler produced samples 20-36 s apart); not
   investigated further.
3. The same cells on a RAM-backed volume directory (earlier supplementary run) still reach only 6-13 K IOPS, so after fixing the
   read-back the next limit is the `lunix-space` thread (`lunix_gc::mark::Mark::unit`, `LsmIndex::get`, `crc32c`, `memcmp` on top of its
   profile, `partA-ramref-perf`).

**Top suspects (no engine code changed):**

1. `crates/lunix-engine/src/destage.rs`, the piece loop of the cut (`ctx.journal.read_at(loc, dst)` per piece, serial per worker, next to the
   `ctx.reader.read_entry` of the cold-chunk read) calling `crates/lunix-journal/src/journal.rs:read_at` (line 340) and
   `crates/lunix-journal/src/sys.rs:read_aligned` (line 163): one `O_DIRECT` read, one allocation and one aligned copy per piece, no
   in-memory copy of records that were just written, no batching or overlap of the reads.
2. `crates/lunix-engine/src/queue.rs` (`try_reserve` -> `Full`, the `ring_wait` park, about lines 505-525) with
   `crates/lunix-engine/src/coord.rs` (the commit trigger near line 359 and C9 `journal_full.store(false)` near line 749): the ring is
   reclaimed only per commit, so one slow destage turns into a stall of the whole commit period for every parked write.
3. `crates/lunix-store/src/container.rs:ContainerWriter::seal` (`fdatasync` per segment, 2-3 % of blocked time) and the `lunix-space` thread
   (`crates/lunix-gc/src/mark.rs:Mark::unit`, `crates/lunix-index` `LsmIndex::get`) once the read-back is cheap.

Percentages are from one host and one device class (network volume, 2-3 K IOPS, 70-140 MB/s) plus RAM; an NVMe-class host was not available,
so the burst and sustained rows are validated only where the device is the bound.

T7-T9 (from the shares):

- **T7, urgent GC mark in steps: not needed.** The urgent pass ran in the RAM cells only: 3-6 calls and 37 `run_urgent` calls per 60 s cell, 1.2-2.8 %
  of the window, at most 0.74 s per call, zero calls on the network volume. It is not what limits the RAM cells (the throttle is). A 0.4-0.7 s hold of the
  coordinator is short next to the seal and zero-rewrite waits; revisit only if the GC term is tuned.
- **T8, segment seals off the packer thread: yes, for devices with a real `fdatasync`.** The seal's `fdatasync` is 30-70 % of the window on the network volume
  (118-207 ms per 16 MiB segment, the destage workers idle meanwhile) and 0.4-1.5 % on RAM, where the coordinator thread that runs the packer
  is at 44-74 % of a core at 0.65 GB/s or 48 K IOPS (it would saturate near 1 GB/s, below the model's 1.5-2 GB/s; not resolved further). Overlapping seals with packing is the largest recoverable wall-clock
  item on a volume; the bandwidth ceiling of the device stays.
- **T9, zero rewrite: yes, with the FREEZE sign-off; try `FALLOC_FL_ZERO_RANGE` first (no format change).** It is 10-36 % of the window and 11-43 % of
  the cuts on the network volume (every ring byte is written twice there: sequential ingest ceiling 40 % of raw with it, 66 % without), and it sits
  in C9, so a parked write is woken only after it. In RAM it is 0.8-5.3 %. Dropping it lifts the sequential ceiling from 28 to 47 MB/s on this
  volume (model). ZERO_RANGE may be as slow on btrfs; measure it before the reader-rule change.

Findings for the lead, outside T7-T9:

1. **Stalls of 21-89 s on the network volume (and 27-41 s in RAM w4k) although cuts last 2-6 s.** Longest ring wait 21 s with a 4.4 s cut: the wake of
   parked writers does not reach every writer cut after cut. In RAM the stalls are the ADR-32 throttle `stop` state.
2. **A full ring for 60 s ends in EIO** (16 KiB seqw rep 2) when a GC compaction pass and the cut share the device (last cut 29.8 s). Space and ring pressure
   and GC compete for one device with no priority for the cut.
3. **GC under random overwrite**: 64 KiB chunks reach amplification 9.8-16 in RAM and fill the volume's space in 10-15 s; sustained rates in RAM are the GC's reclaim rate
   (reclaim_rate about 0.45 MB/s at the stop). The sustained-write row needs a GC term.
4. **Cold read-modify-write is 60-75 % of the chunks** (`cold_rmw` 181 K of 247 K at 64 KiB w4k, 434 K of 696 K at 16 KiB): every partial chunk reads its base chunk
   from the store; on a volume that is raw random-read IOPS at 2.2 K.
5. **16 KiB chunks give 2.0-2.6x the sustained 4 KiB random-write IOPS of 64 KiB** on both device classes (6.7 K / 3.3 K; 47.8 K / 18.1 K), an input to ADR-5.
6. The cut target of 1 s is not reached on the volume: the one-file floor wins (cuts of 2-6 s).

### Stall gate

**Not met on the network volume, but much closer, and no EIO.** Largest completion: 5.1-6.0 s (16 KiB w4k), 7.1-7.3 s (16 KiB seqw), 7.4-12.1 s (64 KiB seqw),
11.5-23.5 s (64 KiB w4k); before 54 / 89 / 38 / 41 s. Nothing above 25 s, no completion error in any cell, no timeout. Where the time goes (status counters of
the write cells, `stall-disk.md`; shares from the uprobe run):

- **Cut length is still the floor, not the wake order.** The ring wait maximum (7.0 s at 64 KiB, 2.6 s at 16 KiB) is one cut: the last cuts take 2.8-7.0 s
  at 64 KiB (15-17 cuts per 60 s) and 0.8-1.4 s at 16 KiB (31-36 cuts; the 1 s target is now about met). A write that finds the ring full waits for the next
  ring file freed, so its wait is bounded by about one cut plus the cut in progress; the previous 21-79 s waits (a write skipped cut after cut) do not occur
  any more: the per-lane deadline never fired, and `freed_files_by_lane` shows both busy lanes (2 and 3, the two queue threads fio's CPUs map to) being freed
  evenly in every cell (8 / 11, 8 / 8, 9 / 8 files per repetition at 64 KiB w4k; 18-26 per lane in the other disk cells), lanes 0 and 1 idle. So lane alternation is not the problem.
- **The cut is the seal waits.** On the volume the coordinator is in `cut_and_commit` 56-76 % of the w4k window (before 78-93 %) and 61-69 % of the seqw window; C1-C4
  (packer, whose segment seals are 44-80 % of the window, 132-169 ms each at 64 KiB: `fdatasync` on the volume) are 97 % of the cut at 64 KiB w4k. T8 (seals off the
  packer thread) is the remaining lever.
- **The pace itself is cheap:** per write at most 18-19 ms in w4k, 42 ms (16 KiB) and 469 ms (64 KiB) in seqw; `ring_paced_writes` 32-55 K per 60 s cell (64 KiB w4k) with 31-53 s of summed delay,
  `ring_pace_capped` 365 once (64 KiB seqw rep 1, 0 elsewhere), pace rate 104 MB/s at the first cut of repetition 1, 15-16 MB/s (the drain rate) in later cuts of the 64 KiB w4k cells. It does not
  add stalls of its own.
- **Most of the large fio maxima are outside the daemon.** Parked writes peak at 256 (`ring_parked_writes`) = 2 busy queues x 128 tags; fio keeps 1,024 writes
  outstanding (8 jobs x 128), so about 768 wait for a tag in the kernel and are not counted in the daemon's wait or in its latency histogram. Evidence: 64 KiB w4k
  repetition 2 has a fio maximum of 23.5 s while the daemon's ring wait is at most 7.0 s and its histogram has no write of 16.8 s or more (writes of 1 s or more: 0.4-0.7 % of all, 4.2 s or more: 181-512 per cell). This is an inference from
  those numbers, not a measurement of the kernel queue. With 16 KiB chunks, where the cut is shorter than 1.5 s, the maxima are 5-6 s.
- Space throttle: zero throttled time, stops and delayed writes on the volume in all cells (it is not involved on this device); GC pressure `normal`; no urgent GC pass.

### Zero step

ZERO_RANGE works on this volume's btrfs: the rewrite function was never called (0 calls in all four shares cells) and the whole C9 reclaim, ZERO_RANGE
included, costs **0.2-0.4 % of the w4k window** (23-54 calls of 5 ms on average, 39 ms at most) and **2.3-4.0 % in seqw** (mean 26-42 ms, 443 ms at most),
against the first T6's zero rewrite of 10.4 % / 24.8 % / 29.4 % / 36 % of the window (11-43 % of the cuts). C5-C9 as a whole fell from 11.5 / 30 / 36 / 53 % to
2.3 / 7.8 / 18.1 / 17.1 % of the window (64 w4k / 16 w4k / 64 seqw / 16 seqw); the rest of C5-C9 in seqw (map seal, checkpoint, index) is not probed separately. In RAM
(tmpfs has no ZERO_RANGE, so the rewrite fallback runs) the zero step is 0.5 / 1.3 / 4.3 / 3.9 % of the window, as before (0.8 / 2.2 / 5.3 / 4.5 %). Segment seals:
80.4 / 43.7 / 54.0 / 41.1 % of the window (before 69.5 / 43 / 53 / 30 %); the urgent GC mark ran only in RAM 64 KiB w4k (11 calls, 1.9 %, `run_urgent` 29 calls 2.5 %).

### Does the ring pace cost burst throughput?

The first 2 s sample (ops counter after fio start) of repetition 1: 64 KiB 104,695 writes against 118,033 (-11 %), 16 KiB 142,585 against 141,650 (+0.7 %). The pace engages at three quarters of the
ring (384 MiB of journal), so most of the ring is absorbed unpaced. On the volume the 8 s burst IOPS: 64 KiB 13,087 / 8,707 / 9,005
(before 14,754 / 8,468 / 8,238), 16 KiB 17,823 / 17,518 / 19,642 (before 17,706 / 13,908 / 13,648): **no measurable cost beyond -11 % in repetition 1 at 64 KiB, within the
first T6's repetition spread**. In RAM, where the ring fills in under a second, it costs: burst 79,139 / 60,012 / 25,120 IOPS at 64 KiB (before 99,946 / 64,675 / 95,864) and 67,354 / 51,656 / 61,614 at 16 KiB
(before 95,909 / 89,916 / 75,002), median -31 % to -37 % at 8 s; sustained RAM IOPS +7 % (64 KiB) and -12 % (16 KiB, inside the first T6's spread).
