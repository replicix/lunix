# M3 report: lunix-journal

- Milestone M3, branch `p1/m3-journal`, base `9d0671a` (origin/main when rebased; the work started at `41fc9aa`), final commit: the
  commit that adds this report (its id is in the final message), 2026-11-12.
- Host: Linux 7.0.0 (aws), 16 CPUs, AMD EPYC, commands pinned to 4 CPUs (`LUNIX_CPUS=12-15`, `-j 4`), rustc 1.98
  1.98.1 (toolchain pinned), no root used. The host was heavily shared during the whole session (load average 200-300), which
  matters for every timing below.
- Ring files lived on the host's ext4 root (a real disk with `write_cache = write through`), under the milestone scratch
  directory; `O_DIRECT` was accepted there.

## What was built (`crates/lunix-journal`)

- `FileJournal` implements `lunix_iface::journal::Journal` (rustdoc is the contract), `FileLane` implements `JournalLane`.
  `JournalConfig`, `TraceEvent` (test hook), `usable_hint` (the D17 checkpoint-tail guard) are the other public items.
- Ring files `journal/q<lane:02x>-<ordinal:08x>.j`, 64 MiB, physically zero-filled (fallocate + zero write), header per
  on-disk-formats 5.1, `chattr +C` best effort, creation = tmp name, zero fill, fdatasync, header, fdatasync, rename, dir fsync.
- Lane: batch packing into pooled aligned buffers, registered as fixed buffers when RLIMIT_MEMLOCK allows (8 MiB on the host,
  so the default 8 x 1 MiB pool falls back to plain writes there), `try_reserve` takes the global `write_seq` under the
  lane's flight lock together with the in-flight registration, one `Slot` outstanding per lane (checked), `submit_read` for any
  lane through a lane-owned aligned buffer, eventfd registered on the lane ring.
- Flush coordinator thread with its own ring: group formation, watermark wait, parallel `fdatasync`, poisoning.
- Recovery (`scan.rs`) with the normative reader from `lunix-format`, merge, first-gap/duplicate stop, `Recovered.damaged`,
  hint skipping with a fallback to a full scan; plus the **wipe plan** (below).
- Reclaim by recycling the inode (zero to the written high-water mark, new ordinal, new generation, rename, dir fsync).
- `journal-lane-bench` binary, crate README, six crash points.

calls the flush latency); the end-to-end `submit_group_flush` to callback latency is also in the bench output
(p50 12-30 us, p99 63-1900 us) and includes thread wake-ups. Readings: with the process on the spike's single CPU the
throughput ratio is 1.02 / 0.84 / 1.12 and the p99 sync ratio is 0.78 / 1.52 / 0.63 (median of the three 1.05); on more CPUs the
scheduler places the coordinator, the io-wq worker and the lane thread on different CPUs and the p99 gets worse (up to
about 6x) on this host (load average 200-300 from other work). With about 550 samples per cell the p99 is the 5th worst
sample, so it is noisy on a shared host: the spike's own p99 varied 20-101 us between runs. I read the rule as met, but
the margin is not demonstrated on a quiet host; please repeat on a quiet one.

Batch policy and its effect: the first version submitted every append while fewer than `max_inflight` batches were in flight,
which made a 64-record group three serial write rounds (0.6x of the spike). The shipped policy (an `append` writes only when
nothing is in flight, `poll` writes while fewer than `max_inflight` are) makes it one parallel round: the first record alone
and the rest packed. Packing cost for the 64-record group: 64 blocks plus the 2 of the lone first record.

Test counts of `lunix-journal` (feature off, in `cargo test --workspace`): unit 1, align 2, contract 13, flush 8, model 4, reclaim 5,
recovery 15 (crashpoints 0: the file is `cfg(feature)`), 48 in all; with `--features crashpoints` 56. Model test wall time 347-433 s for 2 000 sequences
on this host (four threads, load average 200+); `LUNIX_MODEL_CASES=n` sets the total for quick runs.

## rust-skills conflicts

- `err-no-unwrap-prod`: the library has two `unreachable!()` on invariants (`FileLane::active`, the checked `outstanding.take()` in
  `append`); no `unwrap` or `expect` in non-test code. Tests and the bench use `expect` as assertions.
- `unsafe-*`: unsafe is limited to `aligned.rs` (allocation), the ring submissions in `lane.rs` and `coord.rs`, `register_buffers`,
  `getrandom` and the NOCOW ioctl in `sys.rs`; each block has a `SAFETY:` comment; `unsafe_op_in_unsafe_fn` is denied.
- `doc-all-public`: public items are documented; `missing_docs` is not enforced (as in M1).
- `api-non-exhaustive`: `TraceEvent` is `non_exhaustive`; `JournalConfig` has public fields on purpose (a plain tuning struct, built by `new`).
- `lint-cargo-metadata`/`perf-*`: no `hdrhistogram` in the bench (sorted `Vec`), to avoid a new dependency edge.
- `own-*`/`conc-atomic-ordering`: the atomics shared with reclaim use `AcqRel`/`Acquire` where a value gates an action (`inflight`,
  `max_seq`), `Relaxed` for statistics (`fail_any`); the flush wake-up uses `SeqCst` on purpose (a two-flag handshake).

## Decisions taken where the plan was silent

1. **Stale records beyond the stop point are wiped.** Recovery stops at the first gap, but valid records beyond it (an intact
   unflushed tail behind a torn record, or records after a damaged one) stay on disk, and the next incarnation reuses their
   `write_seq`s. A later scan would then find two records with one `write_seq`, or accept a stale record after the new ones and
   apply an old write over a newer, flushed one (the worst failure: a lost acknowledged write). `recover` therefore also plans a
   wipe: per lane, everything after the end of the last record below `next_seq` (and every later file) is zeroed. The wipe,
   the re-initialisation of bad-header files and an `fdatasync` of every file holding records run in the **first `open_lane`**,
   not in `recover`, so fsck can call `recover` read-only (the iface says `recover` is idempotent and runs before lanes). The
   `fdatasync` of surviving records matters too: a read after a process crash can come from a volatile device cache, and no
   later group flush would cover those records. The model test's second incarnation and
   `valid_records_beyond_a_gap_do_not_come_back_in_the_next_incarnation` check this. (Reviewer: please look at `scan.rs::plan_lane`.)
2. **Poison before unreserve.** An aborted append poisons the journal *before* its sequence number leaves the lane's pending set;
   the other order lets a group flush see the lanes clear and complete before the poison is visible.
3. **A reserved slot is part of the flush wait, an append refused after the poison lowers the poison mark** (an append of
   `write_seq` 5 that fails after 9 failed poisons at 5, because a gap at 5 would sit below acknowledged records). A flush
   below the mark is unaffected, as the iface says.
4. **Batch policy** (see the performance section): `append` writes only when nothing is in flight, `poll` while fewer than
   `max_inflight` (2, configurable) are. The queue thread must call `poll` after the wake fd fires (the iface already says so); no
   other call is needed to push a batch out.
5. **Ring geometry:** files per lane = `journal_max / lanes / 64 MiB`, at least two (a lane needs a second file to roll into
   while the first is reclaimed), so with many lanes the real capacity exceeds `journal_max`; `fill().capacity_bytes` is the real figure.
   `JournalConfig::file_len` (64 MiB in production, validated to at least 1 header + 1 maximal record) exists so tests can wrap
   a ring cheaply; the 256 MiB minimum is enforced only for the 64 MiB geometry.
6. **`JournalReserved` accounting:** the charge is the encoded length at `try_reserve`; `ReclaimReport.bytes` is the sum for the
   records in the recycled files. After a restart a file's figure is the sum for the *kept* records in it (those above the
   floor), which is what the engine charges again from `Recovered.records`. The records in a lane's active file stay charged
   until the lane rolls past it and a later reclaim recycles it, so "accounting returns to zero" holds for rolled-away files
   (tested with a ledger/readability identity), not for the active file.
7. **Reclaim guard:** besides `ordinal < tail`, a file is recycled only if no write is in flight in it and its highest `write_seq` is
   at most the largest cut ever given to `tail_after` (initially the floor). A wild tail therefore cannot delete a file holding a
   record above every cut asked for.
8. **`usable_hint(hint, tip_commit_seq)`** is added to the public API: the D17 rule (use the checkpoint tails only if
   `last_commit_seq <= tip commit_seq`) in one tested function for the engine to call; `recover` itself cannot know the tip.
9. **Hint handling:** files below a lane's tail are skipped except the highest valid one; if the resume file turns out to be a
   skipped one, `recover` silently rescans without the hint. A hint with the wrong lane count is ignored.
10. **Files of another volume** (header uuid differs) make `open` fail with `Corrupt` instead of being re-initialised (that would
    destroy another volume's journal); a header that fails its CRC or does not match its name is "bad": reported in
    `Recovered.damaged` as the whole file and re-initialised in the wipe step.
11. **Reducing the lane count** over existing files returns `Unsupported` (their records could not be reclaimed); raising it creates the new lanes' files.
12. **Fixed buffers are best effort:** the pool is registered with `register_buffers`; with RLIMIT_MEMLOCK at 8 MiB (this host)
    the default 8 x 1 MiB pool does not fit and the lane uses plain writes (`Write` instead of `WriteFixed`). Both paths are the
    same code otherwise. (The perf numbers above were taken in the fallback mode.)
13. **Reads:** `submit_read` uses a lane-owned aligned buffer (cached, up to 8), reads the covering block range and copies;
    a reclaimed location completes with `ENOENT`, an out-of-range one is `Invalid`. `read_at` is `pread` on the `O_DIRECT` fd.
14. **Dependency:** `io-uring =0.7.16` was already in `[workspace.dependencies]`; the crate edge (and the crate's `crashpoints`
    feature, `crashpoints = ["lunix-iface/crashpoints"]`) is the separate commit `deps: add io-uring =0.7.16 for m3`, which
    touches `crates/lunix-journal/Cargo.toml` and `Cargo.lock` (the plan words the rule for the root `Cargo.toml`).
15. **Test hooks in the public API** (hidden from docs): `FileJournal::fail_next_append`, `fail_next_sync`, `JournalConfig::trace`.

## Requests to the lead

- Lead's point on stale records after a gap (answered by decision 1): `recover` is read-only and idempotent and returns `Invalid` once a lane
  is open; the first `open_lane` zeroes, on disk and durably (fdatasync before any append), everything each lane holds after its last record
  below `next_seq`, so nothing survives to a second crash. Tests: `valid_records_beyond_a_gap_do_not_come_back_in_the_next_incarnation`,
  `recover_after_a_lane_is_open_is_refused_and_a_second_crash_keeps_stale_records_out` (two crash/recover rounds, new writes passing the stale
  numbers) and phase 2 of the model test. No generation or header field was needed. Proposed iface sentence for `Journal::recover`:
  "Records beyond the stop point stay on disk until the first `open_lane` after `recover`, which durably invalidates them (zeroes each lane's
  tail) before any append; `recover` itself never writes, and returns `Invalid` once a lane is open."

- `tools/ci.sh`: add the crate's crash-point build next to the iface line, because the plan gate needs it and the hosted gate
  should run it:
  ```
  cargo clippy -j "$jobs" -p lunix-journal --all-targets --features crashpoints -- -D warnings
  cargo test -j "$jobs" -p lunix-journal --features crashpoints --test crashpoints
  ```
  (I ran both by hand; the feature is `lunix-journal/crashpoints`, which only turns on `lunix-iface/crashpoints`, so
  `check-features.sh` is unaffected.)
- `lunixd` wiring (M12): nothing in the interfaces had to change. Notes for the engine author: call `usable_hint` before
  `recover`; open all lanes only after `recover` (the first `open_lane` does the wipe and several fdatasyncs, tens of ms);
  `poll` after the wake fd fires is what pushes packed batches out; a `tail_after`/`reclaim` pair needs the cut's commit durable (C9)
  and the floor given to the next `recover` must not be below any cut a `reclaim` already used.
- Spec note for DESIGN 4.1 / ADR-4 (maintainer's call, I did not edit): the stop rule alone is not enough when sequence numbers are
  reused after recovery; the wipe in decision 1 is what makes "ignored after the gap" safe. It deserves a line in 4.1.
