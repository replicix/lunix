## Deviations and open choices (for the reviewer and the lead)

1. **New dependency edge `rustix`** (`rustix.workspace = true` in `lunix-crypto`, already pinned and used by `lunix-iface`)
   for `mmap`/`mlock`/`madvise` of the key arena, which the plan asks for. Not a new crate in the lock, but the plan's
   rule 2 asks to ask first; it is its own commit `deps: add rustix =1.1.4 for m2` (Cargo.lock only). Tell me if it must go;
   the alternative is zeroized heap keys without `mlock`.
2. **Self dev-dependency** (`lunix-crypto = { workspace = true, features = ["test-rng", "tripwire"] }` in
   `[dev-dependencies]`) is how the crate's own tests get the test-only features. `tools/check-features.sh` (normal and
   build edges) stays clean; a release build never has them. Note that `cargo test --workspace` builds one
   `lunix-crypto` shared by the crates under test, with `test-rng` on.
3. **`check_attach` signature.** The plan's positional `(descriptor, credential, supplied_fingerprint, local_pin)` cannot
   unwrap a slot without the keyring, so it is `check_attach(&VolumeDescriptor, keyring: Option<&[u8]>, &AttachRequest)`
   with `AttachRequest { credential, fingerprint, pin, keyring_seq_seen }`, `Credential::{Key, Integrity}(Unlock)`. It
   returns `AttachOk { crypto: VolumeCrypto, record_pin, keyring_seq }` (`record_pin` is the matrix's `Ok+pin`).
   Errors added to the plan's list: `NeedCredential`, `ModeMismatch` (as the matrix says) and `WrongCredential` (a key
   that unwraps nothing, a damaged keyring, a missing key file; outside the matrix; `is_wrong_key_class()`).
4. **The unencrypted tag does not bind kind or family** (D11 as frozen: it covers the extent bytes only). In `plain`
   mode anyone can recompute it anyway (documented limit); in `integrity` mode the tag key is per family, so a cross-family
   move fails, but a node extent opened as a data extent whose `ulen` equals the chunk size is accepted by the codec: the
   map's hash chain is what distinguishes them. The AEAD binds kind and family on `encrypted` volumes (tested).
5. **`verify_id` is ignored for `ExtentKind::Node`**: the interior node hash input (header and child hashes, no
   locations) is not the stored encoding, so the codec cannot recompute it. `chunk_id(Node, data)` hashes the bytes it is
   given (the map passes the hash input); the map verifies node hashes. Documented in `codec::finish`.
6. **FIPS profile**: all derivations and the HMAC chunk id are implemented and vector-tested; `seal` of extents and metadata
   return `Unsupported` (the zero-nonce seal exists only behind `test-rng` for the vector). Opening a FIPS extent is not
   blocked (it needs the zero nonce the decoder enforces), but no FIPS volume can be written.
7. **Error classes**: tag, AEAD and id mismatch are one `Auth { what: "extent" }`; an authenticated extent whose `ulen`
   differs from the volume chunk size, a `dek_gen` above the keyring's, or a bad compressed payload is `Corrupt` (a writer
   bug, not forgery). Header parse errors on encrypted extents precede the AEAD (needed to find the layout) and are
   `Format`; on unencrypted extents the tag is checked first, so every flip is `Auth`.
8. **DoS note**: `unlock` tries every passphrase slot of a keyring; each is bounded (1 GiB, t at most 10, p at most 16) and
   the MAC can only be checked after an unwrap, so a hostile 32-slot keyring costs seconds of CPU and up to 1 GiB at a
   time. Availability only; the read bounds are the format's.
9. **Zeroization limits**: the arena wipes the keys it holds; copies inside aws-lc-rs contexts, BLAKE3 hashers and
   Argon2's block memory (the `argon2` crate's `zeroize` feature is off) are the libraries'. Said in the crate docs.
10. **Tripwire** is per codec instance and unbounded (debug and `tripwire` builds only).
11. `MetaSuite::open` bounds a footer by the kind's loose maximum; the segment store must apply the tighter footer bound
    (`segment::decode_footer_envelope` does). `purpose_key` and `passphrase_kek` are not public outside `test-rng`.
12. An empty passphrase is refused at slot creation; `KeyFile::write_new` also `fsync`s the directory; `KeyFile::read`
    does not insist on mode 0600 (a Kubernetes Secret mount is not).
13. Plan step 8 wording "full seal of 64 KiB <= 1.5 x 3 975 ns" is met by `encrypted`; the `integrity`/`plain` seal
    (7.0 us at 64 KiB, mostly the 64 KiB BLAKE3 pass) has no stated bound.

## rust-skills conflicts

- `lint-missing-docs` / `doc-all-public`: `missing_docs` not enforced (same choice as `lunix-format`); public items carry
  docs, some fields do not.
- `num-cast-try-from`: a few widening or range-checked `as` casts (`ulen32 as usize`, test helpers, bench).
- `err-no-unwrap-prod`: `expect` appears only in `src/bin/cryptobench.rs` and tests.
- `unsafe-miri-ci`: not run; the arena calls `mmap`/`mlock`, which Miri cannot execute.
- `test-doctest-examples`: the doctests are `compile_fail` checks of the key types, no runnable examples.
- `anti-clone-excessive`: `unlock` returns a clone of the decoded keyring next to the root (small, once per attach).
