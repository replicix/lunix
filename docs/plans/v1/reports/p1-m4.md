Design (full text in the crate docs): a shard is a stack of layers under one `std::sync::RwLock`; a layer is a
`BTreeMap<start_lba, Entry>` of non-overlapping intervals; `Entry` is 32 bytes `{seq, offset, ordinal, blocks:u32,
lane, hole}`. **Multi-version** (after the lead's correction of ADR-3 cut semantics): layer 0 holds the newest version
of each block, layer `k` the `k`-th newest. An insert goes to layer 0; what it displaces or what a newer entry shadows
sinks to the next layer. Equal `write_seq` replaces; arrival order never matters. `lookup` reads layer 0; `cut(c)` takes
per block the newest version `<= c` (also when a newer write shadows it); `release(cut)` drops every version
`<= cut_seq`; `dirty_bytes` counts all versions, so the cap bounds them. Neighbours in a layer merge (same seq and
kind, contiguous journal location). Inserts take one shard write lock at a time (a range crossing
stripes is applied stripe by stripe); lookups take one read lock at a time; `cut` takes read locks only and copies
(MVCC by copy: the plan's "persistent structure or versioned entries" choice is "copy at cut"); `release` takes each
shard's write lock once and scans it. No call holds two locks.

## Decisions and deviations

1. **Stripe, not chunk, is the shard unit.** The plan says "64 shards by `lba / chunk`". With one chunk per shard
   unit, a 1 GiB sequential write is at least 16 384 intervals (64 KiB chunks), contradicting "<= 1000 intervals".
   So shard = `(lba / stripe) % shards`, stripe = whole chunks (default: at least 4096 blocks = 16 MiB; configurable
   `stripe_chunks`). A chunk still never spans two shards.
2. **Merging needs equal `write_seq`.** Distinct records have distinct seqs and the per-block seq is required by
   cut/release, so 1 GiB written as 1024 separate records is 1024 intervals; the gate's "1 GiB sequential write" is
   tested as one range or same-seq contiguous inserts. Records' journal locations are also never contiguous (a
   record header sits between them).
3. **Multi-version, as the lead required (ADR-3).** The first version of this report kept one version per block
   (the then single-version `FlatOverlay` semantics); that dropped a write acknowledged by a FLUSH from a cut whenever a
   newer write had already overwritten it. Fixed: superseded versions are kept until released; no `lunix-iface` change
   was needed (the lead clarified the trait docs; rebased on that commit). `release` assumes the cut protocol (no
   insert `<= c` after `cut(c)`, DESIGN 8.1 step 2). A block rewritten N times between cuts costs N versions, counted in
   `dirty_bytes`, so `over_cap()` forces the seal.
4. **Dirty cap:** the trait has only `dirty_bytes`; `OverlayOptions::dirty_cap_bytes` (default 1 GiB, the `B`
   trigger) and `ShardedOverlay::over_cap()` let the engine decide to seal. The cap never blocks an insert.
5. Insert of a range whose end or journal offset overflows panics (documented precondition); zero-block inserts and
   lookups are no-ops.
6. `Cargo.toml` unchanged (`thiserror` declared, unused; the crate uses `lunix_iface::Error`).
