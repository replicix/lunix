## Findings that change the plan's wording

1. **`QUIESCE_DEV` success does not mean "no request in flight".** The driver returns once each
   queue has an idle command left to notify the server with. Requests the engine still holds stay
   held; the first implementation (exit at once after success, as the spike did) aborted its own
   safety check with 9 requests in flight. The layer now waits for the queue threads to end (they
   end only when every command has come back and nothing is in flight), then asks the engine for its
   final commit, then exits. Nothing exits with started requests (W2).
2. **libublk's `wait_and_handle_io` ends as soon as the kernel has aborted the idle `FETCH`
   commands, even while a deferred engine still holds started requests.** It assumes handlers
   complete at once. The layer runs its own loop over `flush_and_wake_io_tasks` and leaves only when
   the queue is down and `started == completed`; until then it waits on the wake fd. Without this a
   queue thread exited with 11 requests held (caught by the `abort()` policy; recovered by
   `REISSUE`, fio rc 0).
3. **A failed `QUIESCE_DEV` is not a no-op** (libublk documentation): the driver leaves the device
   canceling. The plan's "on timeout the daemon keeps serving" is therefore not true; the API says
   so and offers retry or `crash_for_recovery()` (`abort()`).
4. **`TRY_STOP_DEV` answers Busy while udev has the new device open** (seen in the e2e tests); a
   mount is not the only opener. Detach callers retry for a bounded time.
5. `UPDATE_SIZE` on a `DEAD` device dereferences a null disk on kernels before 7.0-rc4; the layer
   refuses it locally.

## Stopped

The e2e run (`device_e2e`, first run) failed five of six tests for two test-code reasons (a counter
read a moment before the last `completed` increment; a detach that raced udev's open of the new
device) and left five devices (ids 0 to 4, all created and recorded by this run, nothing mounted)
without a daemon. A `udev-worker` process then sat in `D` state reading one of them. Per the
rules I stopped, did not retry, and tried only to delete my own recorded devices with
`testd del --id 0..4`; **that command was refused by the session's permission classifier**, so the
devices are still there. `ublk-leftovers` therefore reports NOT clean (the five devices, recorded in
the run's `created-devices`); the `root` wrapper does not mark a wedge file (no script outlived its
grace). Needed from the lead or the user: run
`testd del --id N` for N in 0..4 (each `DEL_DEV` has a 60 s watchdog; nothing is mounted), then
`rmmod ublk_drv`. The test fixes are committed (`settle`, `detach_when_idle`) but untested as root.
The other `D` processes on the host belong to other workloads.

## Deviations and open choices

- Gate runs are incomplete (above). All scripts keep the phase 0 watchdogs; teardown starts a
  serving daemon before any unmount, never signals a stopping daemon, and writes a `WEDGED` marker
  that limits teardown to the own load processes.
- fio ignores `--io_size` with `--time_based`; the crash-loop jobs are bounded by `--runtime` and a
  fixed 1 GiB per job working set. Bounded cells (raw verify, resize) use `--io_size`.
- `DEL_DEV` runs inside the control watchdog (60 s) instead of a separate helper thread: the watchdog
  already is the helper thread.
- Root scripts call their own `df_guard` (twin of `remote.sh df-guard`) before each `mkfs`; the driver
  also calls `remote.sh df-guard` before a run.
- `sudo` clears the environment: scripts get `LUNIX_SPIKE_DIR`, `TESTD`, `LUNIX_ROOT_TESTS` through `env`.
- libublk prints `device reload json failed` once per attach (its control constructor); harmless.
