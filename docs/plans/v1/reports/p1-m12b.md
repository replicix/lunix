### What a crash is

`crash_with` drops the stack without a final commit (after checking no driver is alive), then:
1. **Store (review M2).** The `SyncTracker` undoes, newest first, every rename and unlink no directory `fsync`
   covered (a replaced file's old content is restored; an unlinked file comes back from a graveyard hard link next to
   the volume directory), and cuts every file a rename published or `fdatasync` named back to its last synced length
   (empty when a rename published it unsynced). A store that reports a commit, pack, segment or state file durable
   before syncing it loses it here, and the oracle sees it. Limits: `FsOps` has no create or write call, so a file is
   checked once a rename publishes it or `fdatasync` names it; `lunix-index` syncs with its own calls and the journal
   is separate, so `index/` and `journal/` are outside the hook.
2. **Journal past the flush point.** Every record (lane records and marks) above the flush point is kept, zeroed,
   torn from a 512-byte boundary, or has one byte flipped, at random and independently. The flush point is the larger
   of the driver's bound and the flushed watermark any surviving record or mark carries (ADR-4).
3. **Files never synced.** Every `*.tmp` and `*.open` (outside `journal/`, `cache/`) is deleted, truncated or kept.

## Findings

### E1: `refuse` refused damage that holds no missing number (lunix-engine; fixed on `lead/p1-fixes2`)

`refuse_worthy` refused any damaged range whose `next_seq` was at or below the flushed watermark, although without a
gap such a range can hold only numbers at or below the floor or numbers another lane holds. The first round's model
test met it 4 821 times in 1.2 M ops (about half of all `refuse` opens; the review showed it after a single crash and
a clean close). The maintainer approved the fix (refuse only a duplicate or a gap at or below the watermark); it is on
main. This round: the tolerance arm is gone (any refusal fails the model test), and
`stack_support::refuse_ignores_torn_records_below_the_floor` runs and passes.

### F1, F2, F4 (lunix-fsck, lunix-engine; fixed on `lead/p1-fixes2`)

- F1: fsck did not know the mark ring (a `journal_file` warning per mark file on every volume).
- F2: recovery's index catch-up was not persisted by an idle close (`index_missing` at rest).
- F4 (review): fsck called ordinary crash residue an error.

With the lead's fixes, `lunix-fsck` is exit 0 at rest on every model sequence and every kill run, and reports no
error on any crashed volume (now checked after every model crash, review M4).

### F3: no store sync is ever missing (observation)

The `SyncTracker` undid nothing in 12 558 model crashes: at every drop the store had synced every rename,
unlink and file it had published. That is the result the check exists for; the support test shows the tracker undoes
an unsynced rename, an unsynced unlink, an unsynced publish and an unsynced append.

## Decisions taken (the lead confirms)

1. **One request at a time (accepted deviation, review).** The driver submits sequentially, so the oracle knows the
   `write_seq` order without engine hooks (the stack opens with `NoHooks`). A lane batch therefore holds one record, no
   two batches are in flight, and no cut meets an in-flight write: the damage imitates the on-disk result of
   concurrency, the code paths that produce it do not run here. The M11 model test covers in-flight writes at a cut
   with the same engine; M15 covers concurrency on real devices.
2. **Commit coverage by cut.** A commit makes durable only the requests whose number is at or below its `cut_seq`;
   a grow's FULL commit covers everything before it.
3. **Recovered records are durable.** After a reopen the driver's bound starts at recovery's `next_seq - 1` (the first
   lane open syncs the kept records, on-disk-formats §5.2).
4. **A plain drop must give back the whole oracle (review m2).**
5. **Refuse in half the sequences; any refusal fails.**
6. **Small rings and the background coordinator in the model test (review M3).** 4 ring files of 1 MiB + 64 KiB per
   lane, so every sequence fills, reclaims, reinitialises and wraps them under damage (4 800 ring files reinitialised
   in the gate run). With rings that small a lane can fill between two steps; the background coordinator is on, so the
   commit its fill triggers runs as on a device (the driver thread never blocks in a commit while it holds requests).
   Commits are also forced by the test (`commit_now`, `tick`). Cases are therefore not bit-for-bit reproducible from
   their seed (commit timing).
7. **Crash frequency.** About 1.5 % of the model steps stop the volume (1 % crash with damage, 0.2 % plain drop,
   0.3 % clean reopen).
8. **Kill workload.** A prep child is killed in its first commit (`destage.after_segment_seal:1`), a `*.tmp` is
   planted, and the run child opens that (recovery with replay, sweep and leftover removal), writes about 160 MiB over
   12 commit rounds (production ring files: reclaim and reinitialisation), pauses after some flushes (marks), grows
   once, drops and reopens once, and closes. The child records its durable prefix and the driver's durable
   `write_seq`; after the kill the parent damages the journal above that bound (a power loss on top of the kill,
   review m5) before recovery.
9. **"First, middle, last hit".** From a counting run; a run that timing kept from its hit (the mark points) is
   retried at its own last hit, up to three times.
10. **Expected unreached (review M5).** `index.after_condemn_flag`, `store.evidence.*` (4) and `store.set_aside.*` (3):
    GC state and `fsck --truncate-tip` only. Any other registered point the workload does not reach fails the loop, so
    `gc.*` points fail it the day the collector registers them (M17.B extends the list or the workload).

11. **Waiting for `LOCK` in the tests.** `close`, the crashes and every `TestVolume` open wait until the volume's
    `LOCK` is free. In a multi-threaded test process a closed descriptor can stay held for a few milliseconds: a child
    process another test thread is starting (`lunix-fsck`, a kill-loop child) holds a copy of every descriptor until
    its `exec`, and the `flock` goes with the last copy. Seen 8 times in 12 000 model crashes (at most 8.6 ms) and
    once as `Busy` on a first open. A test artifact, not a store defect; it would matter only to a daemon that starts
    child processes while it holds volumes.

- **R6, `crates/lunixd/tests/startup.rs` (flaky test, cause found).** A detached `tools/ci.sh` run failed
  `a_crashpoints_build_warns_at_start_and_a_normal_build_does_not` with `registry .../state/volumes.json: registry
  i/o: Permission denied`. No root-owned or leftover files were involved: the scratch directory held only files of
  this user. The cause is the other test of the same binary, `a_signal_during_startup_recovery_exits`, which calls
  `lunixd::server::bind` in-process. `bind` sets the **process** umask to `0177` around the socket's `bind(2)`
  (`server.rs:59-61`). When the first test spawns its `lunixd` child inside that window, the child inherits umask
  `0177`, creates `state/` as mode `0600` (no search bit), and cannot read `state/volumes.json`. It passes 3 of 3 when
  run alone. The daemon itself is not affected (it binds once, before it starts any other thread or process). Proposed
  diff (run the two tests one at a time):

  ```diff
  +/// `server::bind` changes the process umask for a moment; a daemon child
  +/// spawned by another test in that window would inherit it.
  +static SERIAL: std::sync::Mutex<()> = std::sync::Mutex::new(());
  +
   #[test]
   fn a_signal_during_startup_recovery_exits() {
  +    let _serial = SERIAL.lock().unwrap_or_else(std::sync::PoisonError::into_inner);
       let Some(t) = common::scratch("startup") else {
  ```
  ```diff
   fn a_crashpoints_build_warns_at_start_and_a_normal_build_does_not() {
  ```
