# ublk + io_uring + Rust as the Lunix data plane

> **Corrections (2026-11-11):** several facts in this note were checked against primary sources in [2026-11-11-fact-check.md](2026-11-11-fact-check.md) (ublk flag kernel versions, provider conditional-write support, prices, latencies, LSVD numbers). Where they disagree, the fact-check wins.

Date: 2026-11-11
Author: research agent (Sonnet)
Question: Is ublk (Linux userspace block driver) driven by io_uring, implemented in Rust, the right data plane for Lunix? Which kernel version should be the floor, which UBLK_F_* flags should be on by default, which Rust crates and threading model fit, what happens on daemon crash/upgrade, how online resize works, what published performance data exist, and how to run it in a Kubernetes pod.

Method note: the 7.0 UAPI header was read locally from `/usr/src/linux-headers-7.0.0-42-generic/include/uapi/linux/ublk_cmd.h` (dev host kernel 7.0.0-31). Docs, kernel source and crates.io were read via web fetch. Items I could not confirm from a primary source are marked UNVERIFIED (section at the end). Kernel introduction versions marked "~" are from memory or inference and need a `git tag --contains` check.

## Summary

- ublk is the right choice. One `/dev/ublkbN` per volume, per-queue io_uring `URING_CMD` rings, no kernel module of our own, and a crash of the daemon cannot panic the kernel. It is the only in-kernel-supported userspace block interface with a real recovery story (USER_RECOVERY), online resize (UPDATE_SIZE) and a zero-copy path. Published numbers: roughly 1.2M 4k IOPS for a single-queue, single-job null target (2022), and about 40M IOPS on 16 queues with auto zero-copy and batching (2025). The data plane will not be limited by ublk itself; Lunix's hash, compress and encrypt work will be.
- Recommended kernel floor: **6.16** (UPDATE_SIZE ~6.15, AUTO_BUF_REG, QUIESCE and PER_IO_DAEMON ~6.16). Recommended target: **>= 6.19** for BATCH_IO, and 7.0 for SAFE_STOP_DEV, NO_AUTO_PART_SCAN and INTEGRITY. Do the feature-probe via `UBLK_U_CMD_GET_FEATURES` at startup and degrade, rather than hard-failing on version strings. Longhorn's SPDK ublk frontend broke on 6.17 because of upstream UAPI changes, so pin and test against specific distro kernels.
- Gotcha on this very host: Ubuntu 7.0 is built with `# CONFIG_BLKDEV_UBLK_LEGACY_OPCODES is not set`. The daemon MUST set `UBLK_F_CMD_IOCTL_ENCODE` and use the `UBLK_U_*` ioctl-encoded opcodes, or ADD_DEV fails. libublk does this by default (to confirm in a spike).
- Zero copy has low value for Lunix. The ublk server never gets to read zero-copy buffers (`Note that the ublk server can never directly access the request data memory`), but Lunix must read every write byte (hash, zero-detect, compress, encrypt). Reads are served from decompressed chunk data, which also needs a CPU copy into the request buffer. Use the plain copy path with pre-allocated per-tag buffers (no NEED_GET_DATA). Revisit `AUTO_BUF_REG` only for a possible raw-passthrough local cache of uncompressed chunks. Zero copy also requires CAP_SYS_ADMIN and is rejected for UNPRIVILEGED_DEV.
- Flush semantics must be advertised explicitly: `UBLK_PARAM_TYPE_BASIC.attrs |= UBLK_ATTR_VOLATILE_CACHE | UBLK_ATTR_FUA`. Without VOLATILE_CACHE the kernel sets no `BLK_FEAT_WRITE_CACHE`, the FS never sends FLUSH, and every write is assumed durable on completion. This is the lever that makes sync mode (FLUSH waits for S3) and async mode (FLUSH waits for local durability or a sync-point barrier) implementable.
- Crash story: without USER_RECOVERY, the daemon dying makes the driver abort in-flight I/O and `del_gendisk()` the device; mounted filesystems see EIO. With `UBLK_F_USER_RECOVERY` (+ `REISSUE`) the `/dev/ublkbN` node and dev_id survive, I/O queues in the kernel, and a new daemon can attach (`START_USER_RECOVERY` / `END_USER_RECOVERY`). Combined with `UBLK_F_QUIESCE` (`UBLK_U_CMD_QUIESCE_DEV`) this gives live daemon upgrade with the FS staying mounted. This should be a day-one design requirement, not a later feature.
- Online grow is a first-class kernel feature: `UBLK_F_UPDATE_SIZE` + `UBLK_U_CMD_UPDATE_SIZE` calls `set_capacity_and_notify()`, which updates the bdev size and emits a resize uevent. The FS still needs `resize2fs`/`xfs_growfs`/`btrfs filesystem resize` (the CSI NodeExpandVolume step). Shrink is the same command but is only safe after the FS was shrunk; Lunix must gate it.
- Rust: **libublk 0.4.8** (crates.io, 2026-08-29; the repo main is 0.5.0 with tokio by default) is actively maintained by Ming Lei, with null/loop/ramdisk/batch examples, recovery, update_size, quiesce, per-IO daemons, batch IO and SHMEM_ZC. `io-uring` 0.7.16 (2026-11-09) is the underlying binding. `tokio-uring`, `monoio` and `glommio` are stale (last release 2024); `compio` is active (0.19.2, Aug 2026) but not what libublk uses. Do not build the queue loop on a general-purpose runtime; use libublk's per-queue thread plus single-threaded executor and offload heavy work to separate pools.
- Container/K8s: running the ublk server in a pod requires `/dev/ublk-control`, `/dev/ublkcN` and the host to create `/dev/ublkbN`. Zero-copy/user-copy/auto-buf-reg devices need CAP_SYS_ADMIN; UNPRIVILEGED_DEV excludes them. Realistically the Lunix node plugin runs as a privileged container (as CSI node plugins do), with the ublk server in its own mount namespace (libublk issue #50: shared mount ns with the FS user can deadlock on daemon exit). Orphaned ublk devices after a pod crash are a known operational problem (Longhorn v2 docs); USER_RECOVERY plus a stable dev_id convention is the fix.

## 1. ublk architecture

### 1.1 Objects and control plane
- `/dev/ublk-control` (misc device, from module `ublk_drv`, `CONFIG_BLK_DEV_UBLK=m` on this host). Control commands are io_uring `URING_CMD`s (not ioctl) with a `struct ublksrv_ctrl_cmd` payload: `UBLK_U_CMD_ADD_DEV`, `SET_PARAMS`, `GET_PARAMS`, `START_DEV`, `STOP_DEV`, `DEL_DEV`, `DEL_DEV_ASYNC`, `GET_DEV_INFO`/`GET_DEV_INFO2`, `GET_QUEUE_AFFINITY`, `GET_FEATURES`, `START_USER_RECOVERY`, `END_USER_RECOVERY`, `UPDATE_SIZE`, `QUIESCE_DEV`, `TRY_STOP_DEV`, and (newest) `REG_BUF`/`UNREG_BUF` for shared-memory ZC.
- Per device: char device `/dev/ublkcN` (the data-plane channel; the server mmaps the `io_desc` array from it and issues `URING_CMD`s on it) and block device `/dev/ublkbN`.
- Lifecycle: `ADD_DEV` (dev_id=-1 for auto) -> `SET_PARAMS` -> open `/dev/ublkcN`, per queue create the ring, `FETCH_REQ` for every tag -> `START_DEV` (blocks until all queues have fetched) -> `/dev/ublkbN` appears. `START_DEV` can return `-EBUSY` if a previously fetched command was canceled. `STOP_DEV` / `DEL_DEV` tear down.
- `struct ublksrv_ctrl_dev_info`: `nr_hw_queues` (u16, max `UBLK_MAX_NR_QUEUES`, clamped to `nr_cpu_ids`), `queue_depth` (u16, 1..`UBLK_MAX_QUEUE_DEPTH`=4096 per queue), `max_io_buf_bytes` (u32, rounded down to PAGE_SIZE; bounds `max_sectors`, i.e. the largest single request), `flags` (u64), `owner_uid/gid`, `ublksrv_pid`.

### 1.2 Data plane (traditional mode)
- One io_uring per queue, ideally one thread per queue pinned to the CPUs returned by `GET_QUEUE_AFFINITY` (blk-mq maps CPUs to the hw queues; the `ublk_drv` queue task is where the request is delivered via task_work).
- `UBLK_U_IO_FETCH_REQ` (per tag, issued at startup): the URING_CMD pends in the kernel; when blk-mq dispatches a request for that (queue, tag), the CQE completes. The request descriptor (`struct ublksrv_io_desc`: `op_flags`, `nr_sectors`, `start_sector`, `addr`) is read from the mmapped io_desc array. The calling task becomes the **daemon** of that (qid, tag); only it may later issue commands for it.
- `UBLK_U_IO_COMMIT_AND_FETCH_REQ`: commits the result (`ublksrv_io_cmd.result` = bytes or -errno) and re-arms the tag in one SQE. Steady state is 1 SQE per I/O on the ublk side plus the SQEs for backend I/O.
- Data buffers (default copy mode): the server supplies a per-tag buffer address in `ublksrv_io_cmd.addr` (FETCH/COMMIT). For WRITE the kernel copies request bio pages into that buffer **before** completing the FETCH CQE (via task_work); for READ the kernel copies out of it when the COMMIT arrives. Buffer size per tag = `max_io_buf_bytes`; total buffer memory = `nr_hw_queues * queue_depth * max_io_buf_bytes` (e.g. 8 x 128 x 512 KiB = 512 MiB), so size deliberately.
- `UBLK_IO_RES_ABORT` (-ENODEV) in a completion means the device is going away: do not re-fetch.
- Docs guidance: dedicated I/O threads, each with its own ring, that "shouldn't handle any control & management tasks". Traditional and batch commands cannot be mixed on one device.

Bit numbers are from the local 7.0 header (SHMEM_ZC / IO_DESC_SIZE come from the current-master header summary and are absent from 7.0). Kernel versions marked "~" are approximate.

Validation in the driver (`ublk_ctrl_add_dev`): `queue_depth` in [1, 4096], `nr_hw_queues` >= 1, `UNPRIVILEGED` + (USER_COPY | ZERO_COPY | AUTO_BUF_REG) -> -EINVAL, `QUIESCE` without `USER_RECOVERY` -> -EINVAL, `INTEGRITY` without `USER_COPY` -> -EINVAL.

## 2. Device parameters (`struct ublk_params`)

`SET_PARAMS` before `START_DEV`; `params.types` bitmask selects the sub-structs: BASIC(1), DISCARD(2), DEVT(4, read-only), ZONED(8), DMA_ALIGN(16), SEGMENT(32), INTEGRITY(64).

- **basic**: `logical_bs_shift` (valid 9..12, <= `physical_bs_shift`; <= PAGE_SIZE), `physical_bs_shift`, `io_min_shift`, `io_opt_shift` (each capped at 256 MiB), `max_sectors` (<= `max_io_buf_bytes>>9`, >= 8), `chunk_sectors`, `dev_sectors`, `virt_boundary_mask`, `attrs`.
- **discard**: `discard_granularity` (must be non-zero), `discard_alignment`, `max_discard_sectors`, `max_write_zeroes_sectors`, `max_discard_segments` (driver accepts only 1 when discard is set). Applied to the queue as `max_hw_discard_sectors` and `max_write_zeroes_sectors`.
- **segment / dma_align**: `max_segments`, `max_segment_size`, `seg_boundary_mask` (+1 power of two; sum >= 4096; zero values are undefined) and DMA alignment. Mostly relevant for ZC/backend alignment.

### 2.1 Flush, FUA, volatile cache (how to make FS send FLUSH)
From `ublk_ctrl_start_dev`: `UBLK_ATTR_VOLATILE_CACHE` -> `lim.features |= BLK_FEAT_WRITE_CACHE`; `UBLK_ATTR_FUA` -> `BLK_FEAT_FUA` (only meaningful together with a write cache; set both); `UBLK_ATTR_ROTATIONAL` -> `BLK_FEAT_ROTATIONAL`; `UBLK_ATTR_READ_ONLY` -> read-only disk.

Semantics for Lunix:
- With `VOLATILE_CACHE` the block layer emits `UBLK_IO_OP_FLUSH` (zero-length) and, for REQ_PREFLUSH|REQ_FUA writes, either a FLUSH before the WRITE and/or sets `UBLK_IO_F_FUA` on the WRITE (when `FUA` is advertised; otherwise the block layer decomposes FUA into WRITE+FLUSH for us).
- Without `VOLATILE_CACHE`: no FLUSH is ever sent, FS assumes write-through. Never use this mode, because it forces completion = durable.
- Therefore Lunix must define durability precisely: a WRITE completion means "in the daemon's volatile state (journal buffer or page cache of the local store)"; FLUSH completion means durable at the configured level (local fsync; or S3 acked in sync mode; or sync-point barrier in async mode). FUA writes complete only when their own data is durable at that level.
- Advertise `discard`: map DISCARD and WRITE_ZEROES to "zero/free extent" metadata ops (cheap, no data stored), which is also what makes the "zero blocks not stored" property fall out for free; honor `NOUNMAP`.
- Suggested values: `logical_bs=4096` (or 512 for compatibility; 4096 halves RMW and map size, but breaks legacy 512e clients, e.g. some VM images; make it a creation-time option), `physical_bs=4096`, `io_min=4096`, `io_opt` = chunk-friendly size (e.g. 64 KiB-1 MiB), `max_sectors` = 1 MiB (2048) is a good start (UNVERIFIED limits: `max_io_buf_bytes` upper bound), `discard_granularity=4096`, `max_discard_sectors` large (e.g. 4 GiB worth) since discard is O(metadata).

## 3. Crash / restart story

Without recovery flags (observed from `ublk_drv.c`): when the last holder of `/dev/ublkcN` closes (daemon exit/crash), `ublk_ch_release` -> work item aborts outstanding I/O (`ublk_abort_queue` fails requests the server owned), then `ublk_stop_dev_unlocked()` -> `del_gendisk()`. `/dev/ublkbN` disappears, a mounted FS gets EIO (journal abort / remount-ro on ext4 errors=remount-ro), and the dev_id remains until `DEL_DEV`. This is unacceptable for a block device that backs a pod's data.

With `UBLK_F_USER_RECOVERY` (and at most one of REISSUE / FAIL_IO):
- Daemon exits -> device becomes QUIESCED (or FAIL_IO for the FAIL_IO variant). `/dev/ublkbN` and dev_id persist. Not-yet-delivered requests wait in blk-mq (requeued); delivered-but-uncommitted are aborted (base mode), re-queued (`REISSUE`), or failed (`FAIL_IO`, which also fails all new I/O during the absence).
- New daemon: `START_USER_RECOVERY` (before opening `/dev/ublkcN`), open cdev, rebuild queues and re-`FETCH_REQ` all tags, **re-issue `SET_PARAMS`** (UNVERIFIED whether the params are retained by the driver; libublk's recovery path rebuilds target data from its exported JSON under the run dir), then `END_USER_RECOVERY` -> unquiesce and I/O flows.
- Planned upgrade: old daemon calls `QUIESCE_DEV(timeout)` (needs `UBLK_F_QUIESCE`, which requires USER_RECOVERY), completes in-flight work, returns `UBLK_IO_RES_ABORT` for re-fetching tags, exits; new binary starts recovery. A mounted FS only sees a pause. `-EBUSY` means the I/O did not drain in the timeout.
- Choice for Lunix: `REISSUE`. Re-delivered block writes/flushes are idempotent for a block store (same LBA, same data; concurrent in-flight writes had no mutual ordering anyway). The kernel doc suggests REISSUE for backends tolerating duplicate writes, which a content-addressed store does (a second chunk put is a no-op). `FAIL_IO` as a configurable policy for "fail rather than hang" (e.g. when the pod is being killed). A hung-queue timeout (watchdog that flips to FAIL_IO via control plane) is worth adding to avoid indefinite D-state processes.
- Daemon state that must be recoverable without the old process: volume metadata (extent map, journal) must be on the local store with a clean/dirty marker, and writes accepted but not yet flushed in the old daemon are lost on a crash (legal under FLUSH semantics, as long as FLUSH-ed data survived).
- Mount-namespace deadlock (libublk-rs issue #50): if the daemon shares its mount namespace with a process that mounted the device, daemon exit can trigger an unmount flush that needs the dead daemon -> deadlock. Run the ublk server with `unshare(CLONE_NEWNS)` / separate mount ns. Likewise never place the daemon's own local store (or its logs) on a ublk device it serves; and avoid swap/page-fault paths that depend on it.
- Operational: a crashed Longhorn v2 instance-manager can leave orphaned ublk devices that are sometimes only removable by node reboot (Longhorn docs). Mitigate by always using USER_RECOVERY, a persistent dev_id<->volume map, and `DEL_DEV_ASYNC` (6.14-ish) for cleanup of stuck devices.

## 4. Online resize

- Kernel: `UBLK_F_UPDATE_SIZE` + `UBLK_U_CMD_UPDATE_SIZE` (control, 0x15, size in 512-byte sectors in `cmd->data[0]`). The handler takes `ub->mutex`, requires a live disk (a March 2026 fix for a NULL deref when called before START/after STOP now returns `-ENODEV`; ensure the kernel has it, stable-tagged), sets `params.basic.dev_sectors` and calls `set_capacity_and_notify(ub->ub_disk, dev_sectors)`. That updates the gendisk capacity, the bdev inode `i_size`, and sends a `KOBJ_CHANGE` uevent with `RESIZE=1`.
- Grow: block layer and mounted FS can be expanded online: ext4 `resize2fs /dev/ublkbN`, xfs `xfs_growfs <mnt>`, btrfs `filesystem resize max`. In K8s the CSI `ControllerExpandVolume` (Lunix control plane updates volume metadata, adds capacity to the extent map, calls UPDATE_SIZE) then `NodeExpandVolume` (FS grow). Raw block volumes need only UPDATE_SIZE. The kernel does not grow the FS automatically.
- Shrink: the same command with a smaller size. The kernel will truncate the bdev; I/O beyond the new end gets EIO. Safe only if the FS has been shrunk (ext4 offline only; xfs cannot shrink; btrfs online). Lunix should: (1) refuse shrink unless the caller asserts the FS was shrunk, (2) before calling UPDATE_SIZE, read the highest non-zero LBA from the extent map and refuse if data exists beyond the new size unless forced, (3) afterwards, trim extents beyond the new end (they become garbage for the chunk GC).
- Sizes must be persisted: after daemon restart (recovery or fresh), `dev_sectors` in SET_PARAMS must equal the current persisted size.
- libublk-rs: `UblkCtrl::update_size(dev_size_bytes)` (takes bytes) and `quiesce_dev(timeout_ms)`, `start_user_recover()`, `get_params/set_params`, `kill_dev/del_dev/del_dev_async`, `get_features()` (since 6.5).

- Examples in repo: `null.rs`, `loop.rs` (async, `-z` = AUTO_BUF_REG zero copy using `read_at_fixed`/`write_at_fixed`, `-T n` threads per queue via PER_IO_DAEMON, `-S` sequential tag partition), `ramdisk.rs` (single-thread async for both control and I/O), `batch.rs` (BATCH_IO). Downstream project `rublk` (null, loop, zoned, qcow2, compress, vram targets) is a good code reference for a stateful target with a compression layer.
- Quick-start shape: `UblkCtrlBuilder` (name, id, nr_queues, depth, io_buf_bytes, flags, `io_threads_per_queue`, dev_flags such as `UBLK_DEV_F_ADD_DEV`/`RECOVER_DEV`), `run_target(tgt_init, queue_fn, device_fn)`; queue_fn runs one per queue thread; async I/O is expressed as `.await` on typed ops and `COMMIT_AND_FETCH` is handled by the library.
- Self-reported performance: null target, 2 queues, QD 64 about equals blktests' C `miniublk`; copy-based loop caps near 450K 4k IOPS per submitter thread; 8 submitters at `-d 128` ~3M 4k IOPS vs ~1.9M at `-d 64`; `-T 2` ~800K, `-T 4` ~1M for a single submitter; at QD1 `io_threads_per_queue` gives no gain and about 1 us more latency. PER_IO_DAEMON needs 6.16+.
- Caveats: recovery documentation in the README is thin (but API exists: `start_user_recover`, dev flag for recover), unprivileged mode needs udev scripts (`utils/ublk_chown.sh`), mount-ns caveat above.

Pairing guidance: libublk owns the per-queue ring and tag state machine. It is itself built for the thread-per-queue model, so a second async runtime on those same threads is not needed and mostly harmful (two event loops, two rings). Everything else (S3 client, metadata, GC, compression pool) belongs on other threads/runtimes. If libublk's abstraction ever blocks us (e.g. custom SQE batching, multishot, registered files for the local store), drop one level to the `io-uring` crate plus libublk's `sys` bindings; the control plane can stay on libublk's `ctrl`.

Thread-per-queue model:
- `nr_hw_queues` = min(physical cores reserved for I/O, 8-16 initially); `queue_depth` 128-256 (device-wide depth = queues x depth). Per queue: one pinned thread (affinity from `GET_QUEUE_AFFINITY`) with one io_uring (`SINGLE_ISSUER | DEFER_TASKRUN | COOP_TASKRUN` where applicable, SQPOLL not recommended for packed pods), one slice of preallocated, mlocked, hugepage-backed buffers.
- Queue thread does only: parse descriptor -> index lookups in memory -> dispatch. CPU-heavy steps (BLAKE3 hashing, zstd/lz4, AES-GCM/XChaCha, zero detect) run inline for small requests or on a worker pool (with BATCH_IO any worker may commit any I/O; without it, completions must be bounced back to the owning daemon thread via an eventfd/ring message because commands can only be issued by the (qid, tag) daemon).

## 6. Performance: published numbers and pitfalls

Data points (all from different kernels/hardware; no apples-to-apples ublk vs null_blk table was found):
- ublk-null, 1 queue/1 job, 4k direct IO: ~1.2M IOPS (Ming Lei, original 2022 slides, io_uring/libaio).
- ublk zero copy on null target: up to ~5x IOPS at 64k/512k block size vs copy (2023 fused-cmd series; mechanism since replaced by buffer registration). Reports say >= 256 KiB requests benefit "a lot".
- BATCH_IO (2025 cover letter): `kublk add -t null -q 16 --auto_zc -d 512`, fio `t/io_uring` pinned to 32 CPUs, 16 jobs: ~40M -> ~42M IOPS (+5%). Shows the ublk framework itself reaches tens of millions of IOPS on a null target.
- Copy path (Nov 2025): Caleb Sander Mateos's `copy_{to,from}_iter()` rework for user copy; Ming reported ~40% throughput improvement on the selftest null server with ZC disabled. Hence kernels >= 6.19 (probably) are materially better for copy-mode.
- vs NBD (2022 LKML ublk-qcow2 thread, single job, same preallocated qcow2): ublk ~99k randwrite / ~110k randread IOPS vs qemu-nbd ~25k / ~31k. Maintainers caution about confounds (a ublk export in qemu-storage-daemon was suggested for a fair test). Vitastor (vendor, 100G TCP): 4k randwrite Q128 ~149k ublk vs ~91k NBD vs ~95k VDUSE; linear reads ublk 2076 MB/s vs NBD 1885 vs VDUSE 1800.
- vs loop: ublk-loop reported "basically same function" and roughly on par with kernel loop (2022 cover letter, excerpt cut off, no numbers).
- Longhorn v2 (SUSE docs): UBLK frontend "may" beat the default NVMe-oF frontend only on high-end setups (millions of IOPS, many cores), is experimental, needs kernel >= 6.0 and `ublk_drv`, and was documented as broken on kernel 6.17 (EINVAL / reportedly panic).
- Not found: published numbers for ublk vs SPDK vhost-user-blk, vs TCMU/LIO loopback, vs BUSE. Qualitative: BUSE (NBD-like socket transport) and TCMU (shared-memory ring + SCSI) have more per-I/O overhead and no recovery story; vhost-user-blk is for VMs not host block devices; SPDK's ublk target is the SPDK bdev layer over ublk (the same kernel interface), so SPDK's advantage is its polled user-space backend, not the front end. KVM Forum 2024 (Red Hat, "out of process storage backends") compares in-process, NBD, ublk, vhost-user-blk, vhost-vdpa and FUSE, but only chart labels were extractable.

Pitfalls to design around:
1. **Memory-reclaim deadlock**: the daemon must never need to allocate or fault in memory that can only be freed by writing to its own device (dirty pages of its own volume). Mitigations: `mlockall(MCL_CURRENT|MCL_FUTURE)`, preallocate all queue/worker buffers, `prctl(PR_SET_IO_FLUSHER, 1)` (Linux 5.6+; makes the daemon exempt from the "reclaim through own device" deadlock; requires CAP_SYS_RESOURCE), avoid allocator growth in the hot path, keep S3 client memory on a bounded budget, never put swap or the local store on the served device.
2. **Page-cache double caching**: the FS above ublkb already has a page cache. If the local store is files on a FS, write them with `O_DIRECT` (or `RWF_DSYNC`/`fdatasync` discipline) or you cache every byte twice (once in the guest FS page cache, once in the host page cache of the backing files) and also lose control of the "durable" point. Use io_uring with registered files and fixed buffers on the backing files. A segment/log-structured local store with explicit `O_DIRECT` + `fdatasync` matches the FLUSH model best. On XFS/ext4, preallocate (fallocate) and use aligned O_DIRECT to avoid metadata journaling on the hot path.
3. **Backing-file O_DIRECT alignment**: 4 KiB (or device logical block) alignment for buffers, offsets and lengths; compressed chunks are variable length, so pack into aligned segments/blocks.
4. **Request splitting / segment limits**: set `max_sectors` to a multiple of chunk size and `io_opt` to the chunk-friendly size; a request that straddles chunks means RMW.
5. **Per-I/O page pinning / task_work cost**: ublk copy-mode pays a copy in kernel task_work in the daemon's context; large `queue_depth` x `nr_hw_queues` x `max_io_buf_bytes` multiplies memory. Prefer fewer, deeper queues over many shallow ones when the backend is CPU-heavy.
6. **Single-threaded queue starvation**: one slow synchronous call (S3 network, mutex, page fault) in the queue thread stalls every tag on that queue. All blocking work goes off-thread.
7. **Latency at QD1**: libublk found PER_IO_DAEMON hurts QD1 (about +1 us); only enable it for batched/deep workloads. Also consider SQPOLL/`IOPOLL` only if the pod has dedicated cores.
8. **Kernel API churn**: 6.17 broke Longhorn's SPDK ublk; gate on `GET_FEATURES` and test per distro kernel. The 2026-03 `ublk_ctrl_set_size` NULL-deref fix and the 2026-03 partition-scan fix show the newer features are still being hardened.

## 7. Security and containers

- `/dev/ublk-control` is root-only by default; a udev rule can make it available to an unprivileged user, and then (with `UBLK_F_UNPRIVILEGED_DEV`) every control command except ADD_DEV is restricted to the owner and re-checked against the `/dev/ublkcN` path passed in `dev_path_len`/payload (so a device created in one container can only be controlled there). Info queries use `GET_DEV_INFO2`. Udev rules chown `/dev/ublkcN`/`ublkbN` to the stored `owner_uid/gid` (libublk-rs ships `utils/ublk_chown.sh`, `ublk_user_id`).
- UNPRIVILEGED_DEV forbids USER_COPY, ZERO_COPY and AUTO_BUF_REG because a malicious server could leave request buffers uninitialized and leak kernel memory. Also, unprivileged mode drops some recovery flags (driver code shows a mask on REISSUE; exact rule UNVERIFIED), so it is not suitable for our recovery-based design.
- In Kubernetes: nothing in the sources I found describes a production CSI that runs ublk unprivileged. Observed practice: (a) Longhorn v2 / SPDK instance-manager pod runs privileged with host `/dev` and `ublk_drv` loaded on the node; (b) DDN EXAScaler CSI documents "`ublk_drv` module on the node + userspace client installed" for `volumeMode: Block`; (c) Vitastor documents a ublk frontend. All rely on node-level module loading and privileged access.
- Practical constraints: the kernel creates `/dev/ublkbN` and `/dev/ublkcN` in the **host devtmpfs**. A non-privileged container has its own `/dev` tmpfs and device cgroup (major numbers for ublkb/ublkc are dynamic), so a plain pod will not see them. A CSI node plugin needs `privileged: true` (or `CAP_SYS_ADMIN` + hostPath `/dev` + device cgroup allow rules for `b *:* rwm` and the ublkc major) and `mountPropagation: Bidirectional` for the staging path anyway. The user's workload pod gets either the raw block device via the CSI `NodePublishVolume` bind mount (volumeMode Block) or a mounted FS, never the ublk nodes directly.
- Sidecar design recommendation: the data-plane daemon (the thing holding `/dev/ublkcN` open) should run as a **node-level DaemonSet / systemd unit**, not as a per-pod container, so that (1) a workload pod crash/eviction doesn't take the device down, (2) the daemon survives CSI-plugin restarts, (3) the mount ns issue can be handled once. The CSI node plugin talks to it over a Unix socket (create/attach/resize/detach/add-backend). This also fits cross-region pod migration: detach on node A (SAFE_STOP_DEV / TRY_STOP_DEV, flush, final sync point), attach on node B (cold cache).
- Hardening: seccomp must allow `io_uring_setup/enter/register`; many hardened runtimes and `kernel.io_uring_disabled` sysctl (0/1/2) block io_uring. Check `io_uring_disabled=0` (or 1 with a group) on nodes. gVisor/Kata/ Firecracker-type runtimes won't expose ublk at all.

## Recommendations for Lunix

1. **Kernel floor**: 6.16 (hard); **supported/tested**: 6.19+ and 7.0 LTS-like distro kernels; use `UBLK_U_CMD_GET_FEATURES` at startup to enable BATCH_IO / SAFE_STOP / NO_AUTO_PART_SCAN when present and to refuse to start if the mandatory set {CMD_IOCTL_ENCODE, USER_RECOVERY, QUIESCE, UPDATE_SIZE} is missing. Keep a "compat" code path without BATCH_IO. Publish a tested-kernel matrix; CI against the distro kernels customers use.
2. **Default flags**: `CMD_IOCTL_ENCODE | USER_RECOVERY | USER_RECOVERY_REISSUE | QUIESCE | UPDATE_SIZE | NO_AUTO_PART_SCAN | SAFE_STOP_DEV`, plus `BATCH_IO` when available (>= 6.19), plus `USER_COPY` if benchmarks show it wins (spike). Never: NEED_GET_DATA, URING_CMD_COMP_IN_TASK. Not default: SUPPORT_ZERO_COPY/AUTO_BUF_REG (we have to read the data), UNPRIVILEGED_DEV (loses fast paths), SHMEM_ZC, ZONED, INTEGRITY. Allow `FAIL_IO` as per-volume policy (instead of REISSUE) and an `unprivileged` dev mode for developer laptops/CI.
3. **Params**: BASIC with `attrs = VOLATILE_CACHE | FUA` (no READ_ONLY unless the volume is a snapshot/restore mount), 4096 logical/physical, `io_opt` = chunk-friendly, `max_sectors` 1 MiB initially; DISCARD with `max_write_zeroes_sectors` and large `max_discard_sectors`, `discard_granularity=4096`. This makes mkfs/fstrim cheap and keeps zeros out of the store.
4. **Queue model**: libublk, one pinned thread per queue, `nr_hw_queues` 4-16 configurable, QD 128-256, preallocated mlocked buffers; `PR_SET_IO_FLUSHER` + `mlockall`; in its own mount namespace; control plane on a separate thread/runtime. Heavy CPU (hash/compress/encrypt) on a bounded worker pool; with BATCH_IO any worker can commit completions; without it, post completions back to the owner queue thread. S3 uploader/downloader on its own tokio multi-thread runtime; never on the queue threads.
5. **Runtimes**: use libublk (pin an exact version; prefer 0.4.8 until 0.5.0 is released, and evaluate 0.5.0's tokio-current-thread `UblkRuntime`). Add the `io-uring` crate (0.7.x) directly for the local-store files (registered files, fixed buffers, `O_DIRECT`, linked `WRITE -> FSYNC`). Don't adopt tokio-uring/monoio/glommio (stale); watch compio only as a possible replacement for the non-ublk side.
6. **Recovery first**: design the process around restartability: all durable state (journal, extent map, dirty set, S3 sync-point watermark) on the local FS with an fsync ordering protocol; daemon startup path = "attach if device exists in QUIESCED/FAIL_IO state (`START_USER_RECOVERY`), else ADD_DEV". Implement `lunixd upgrade` as `QUIESCE_DEV` -> exec new -> recover. Hung-device watchdog switches to FAIL_IO.
7. **IO path sketch (ublk request -> local store)**:
   - `FETCH` CQE -> read `ublksrv_io_desc` (`op = op_flags & 0xff`, `start_sector`, `nr_sectors`, `UBLK_IO_F_FUA`).
   - READ: map LBA range -> extent map (in-memory, sharded by chunk index) -> per chunk: hole/zero -> memset 0; else locate stored chunk (hash -> segment offset) -> read compressed bytes from the local store (io_uring `READ_FIXED` on O_DIRECT segment file, or in-memory chunk cache hit) -> decrypt/decompress on a worker -> copy the requested sub-range into the tag buffer (or `pwrite` to cdev with USER_COPY) -> `COMMIT_AND_FETCH(result = bytes)`. If chunk is not local (S3-backed cache miss) -> park the tag, issue a GET, coalesce concurrent misses, complete when filled.
   - WRITE: stage data in the tag buffer; split on chunk boundaries; partial chunk -> RMW (read old chunk, patch). Per full chunk: all-zero check (SIMD memcmp) -> record "zero" in the extent map and drop any previous mapping; else hash (BLAKE3, keyed if encryption on) -> dedup lookup in the chunk index -> miss: compress, encrypt, append to the current local segment (write-back to a log) -> update extent map and the metadata journal record (LBA range -> chunk id). Completion = "in journal buffer" (volatile, since VOLATILE_CACHE is set). With FUA flag, wait for the segment+journal fsync before completing.
   - FLUSH: group commit. Collect all outstanding flushes, issue one `fdatasync` on the open segment + journal (in a single `io_uring` linked batch), then (sync mode) wait for the S3 upload and commit marker of everything up to this watermark; (async mode) mark the watermark for the next sync point and complete after local durability. Completion -> `COMMIT_AND_FETCH(0)`.
   - DISCARD / WRITE_ZEROES: extent-map update + journal record, no data movement; honor `NOUNMAP` by still recording zero (never storing); return success quickly.
   - Out-of-space (below free-space floor): per-volume policy; either park tags in a wait list until space is signalled or complete with `-ENOSPC` (maps to EIO/ENOSPC at the FS); never block the queue thread itself.
   - Back-pressure: cap in-flight dirty bytes; stall new WRITE completions (not the thread) when the journal/segment writer is behind.
8. **Containers**: ship the daemon as a node-level DaemonSet (privileged) controlling devices via a Unix socket from the CSI plugin; document `modprobe ublk_drv`, `io_uring_disabled=0`, and a host-side udev rule for ownership; provide a startup self-check that reports kernel/config (`BLKDEV_UBLK_LEGACY_OPCODES`, features) before accepting volumes.
9. **Spikes to run before committing** (each < 1 day): (a) null + loop targets from libublk on this 32-CPU host vs `null_blk` and `zloop` for a baseline table; (b) copy-mode vs USER_COPY vs BATCH_IO at 4k/64k, QD 1/32/128; (c) a recovery cycle under `fio` + mounted ext4 with kill -9 and with QUIESCE, checking fsck cleanliness; (d) `UPDATE_SIZE` grow with `resize2fs` online; (e) FLUSH/FUA visibility test: confirm `/sys/block/ublkbN/queue/write_cache` shows `write back` and `fua` is 1, then count FLUSH ops per `fsync()` in the daemon.
