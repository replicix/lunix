# What Lunix can reuse from Constellation

Date: 2026-11-11
Author: research agent (Sonnet)
Question: Lunix (a ublk/io_uring block-device daemon with hash-addressed, deduplicated, compressed, optionally encrypted chunks, local FS as store/cache, and one or more mirrored S3 backends) is the block sibling of Constellation (`/home/bra/cvs/replicix/constellation`, Rust workspace, distributed POSIX FS on S3). This note studies the Constellation code and docs and says, component by component, what Lunix can depend on, extract into a shared crate, copy as a design, or should not reuse. All paths below are relative to `/home/bra/cvs/replicix/constellation` unless absolute. Everything was read from source and docs; nothing was built, run or benchmarked by me.

## Summary

- **Constellation's data plane is close to what Lunix wants, and it is already format-stable**: fixed-size chunks (4 MiB default, power of two 1-64 MiB), identity = blake3 of the *uncompressed plaintext* (keyed blake3 in E2E mode), self-describing 16-byte object header (`CCH1`, version, codec u16, level, uncompressed length), zstd or raw with an "incompressible -> store raw" guard, compress-then-encrypt with XChaCha20-Poly1305 (random 24-byte nonce, chunk hash as AAD). Lunix can adopt this verbatim as its chunk object format, which also makes Lunix chunks readable by Constellation tooling.
- **Fixed chunks suit a block device better than they suit a FS; CDC would be wrong for Lunix** (LBA -> chunk is `lba / chunk_size`). But 4 MiB is too large for a block device's random 4 KiB write pattern. Lunix should choose its own default (suggest 64 KiB-1 MiB; see Recommendations) and needs a pack/segment layer that Constellation has only for *metadata* (`packs/`), not for data chunks (ADR-11 deferred data packing; one S3 object per chunk).
- **No all-zero detection exists in Constellation** (only sparse "holes" in manifests = missing indices, `crates/fs-core/src/manifest.rs`). Lunix must write its own (trivial: SIMD compare against zero page, then a sentinel entry in the block map; do not store or hash).
- **The S3 conditional-write protocol is the most valuable thing to reuse.** `crates/store-s3/src/cas.rs` (`put_conditional`, `Verify::Body` read-back to detect "my own retried write landed"), `probe.rs` (`probe_cas_semantics`, doctor checks incl. 8-way concurrent create/swap and versioning), `classify.rs` (transient vs permanent errors), `lease.rs` (CAS lease + epoch fencing), `commits.rs` (immutable CAS-created `commits/<seq>` objects + "nothing a commit names may be missing" invariant). These encode real provider quirks (409 vs 412 vs 304 vs 404 across AWS/MinIO/R2/OVH) found on live runs.
- **The commit chain is the model for Lunix's crash-consistent S3 snapshot**: upload all chunks/map nodes first, then CAS-create `commits/<seq>` naming a root hash. A crash before the CAS leaves only garbage; after it, a mountable state. This is exactly Lunix's async-mode requirement. The prolly-tree `mtree` crate (canonical Merkle map; root hash = snapshot; diff O(difference)) is a good fit for the LBA -> chunk map, with a different key codec.
- **Crate reuse is mixed.** Self-contained today: `constellation-upload-concurrency` (only tokio), `constellation-types`, `constellation-mtree` core (`blake3`, `thiserror`, `types`), `constellation-fs-core` (blake3/bytes/region/serde, but FS-shaped types). **`constellation-store-s3` is NOT standalone**: it depends on `fs-core`, `mtree`, `platform` (clock, `native()`), and is FS-shaped (leases/logs/inbox/nodes/designation). Recommend extracting a small `object-cas`/`chunkstore-core` crate rather than depending on all of store-s3.
- **Local cache**: `crates/fs-core/src/cache.rs` `DiskCache` (LRU over clean, pinned/dirty never evicted, temp+`fdatasync`+rename, startup rescan, reserve-before-accept ENOSPC) is a decent *design* template, but it is whole-chunk, mutex-protected and file-per-chunk; for Lunix's cache (write-back, sub-chunk dirtiness, block-device fsync semantics) copy the design, not the code.
- **Metadata store is fjall 3 (LSM)**, vendored with two patches (`vendor/fjall`, `vendor/lsm-tree`). Constellation's own ADR-9 benchmark disqualified fjall for lookup-heavy loads (4K/s untuned point reads) before plan 29 switched to it with tuning. Lunix's block map is far smaller and simpler; evaluate fjall vs. a flat mmap'd/append-log map before inheriting the vendored patches.
- **Runtime/IO**: Constellation is tokio multi-thread + blocking pools + rayon private pools; io_uring appears only as the FUSE-over-io_uring transport (via a forked `fuser`), not for disk or S3 I/O. There is no ublk code. Its FUSE benchmarks (io_uring transport 3.25x IOPS, 4.7x less CPU) are good evidence for the io_uring bet but not reusable code.
- **CSI**: `crates/csi` (~24k lines incl. tests) is tightly coupled to Constellation's engine pods, FUSE fd handover and control protocol. Reuse the *shape* (identity/controller/node split, `volume_id` codec, credential injection over a control socket, Helm chart privilege split, `csi.proto` v1.13.0 vendored under `crates/csi/proto/`), not the crate. Constellation's CSI explicitly does **not** do block volumes.
- **Security audit (Sept 2026)** is directly applicable: bounded zstd decompression (`decompress_bounded`, declared-length ceiling), bounded `Vec::with_capacity` on decoded counts, authenticated `meta.json` to stop E2E downgrade, trust-nothing decoders for anything fetched from a bucket, loopback API DNS-rebinding guard.

## 2. Data plane

### 2.1 Chunking
- **Fixed-size**, not CDC. `crates/fs-core/src/chunk.rs`: `ChunkLayout { chunk_size: u32 }` with `chunk_count`, `chunk_len`, `slices(offset, len) -> ChunkSlice{index, offset, len}` (offset math is `offset / chunk_size`). Default 4 MiB, per-FS `fs create --chunk-size`, power of two 1-64 MiB, recorded per file in the manifest (DESIGN.md section 3). Changing chunk size breaks dedup between old/new data (documented).
- CDC is *format-reserved only* (`ENTRY_CDC = 4` in `crates/fs-core/src/manifest.rs`; ADR-11 explains: complicates offset->chunk mapping, RMW and sparse handling, only pays for shift-heavy whole-file rewrites). For a block device a shift never happens (blocks are addressed by LBA), so fixed chunks are strictly right for Lunix.
- `ChunkLayout::slices` is directly reusable for Lunix's LBA-range -> chunk-slice splitting, including partial-chunk read-modify-write.

### 2.2 Hash and addressing
- `ChunkHash([u8;32])` = `blake3::hash(plaintext)`; E2E mode `ChunkHash::keyed(key, data)` = `blake3::keyed_hash`. Hex via allocation-free `hex_ascii()`. (`crates/fs-core/src/chunk.rs`)
- Identity is of the *uncompressed plaintext* (ADR-10): independent of codec/level/encryption, so changing compression never invalidates dedup and peers can verify without agreeing on encoding.
- S3 key: `chunks/<aa>/<bb>/<hash-hex>` (`crates/store-s3/src/layout.rs`, `chunk_key`). Two shard levels exist for LIST parallelism (the GC orphan sweep scans 256 prefixes) and for directory-backed S3 implementations, not for AWS partitioning (AWS partitions on arbitrary key-byte positions; DESIGN.md section 2 spells this out). Flat object namespace elsewhere: `packs/`, `blobs/`, `commits/<seq:016x>`, `leases/`, `meta.json`.
- Zero-padded hex sequence numbers make lexicographic = numeric order, so "LIST with offset" is a seek (reused trick; useful for Lunix commit/segment keys).

### 2.3 Packing
- **Data chunks are not packed**: one S3 object per chunk. Pack for data (`ENTRY_PACK = 3`, git/restic-style ~64 MiB packs) is explicitly deferred in ADR-11 because GC becomes compaction.
- **Metadata nodes are packed** (`crates/store-s3/src/packs.rs`, `PackStore`, `build_packs`, `PackIndex`): `packs/<hash>` + sibling `packs/<hash>.idx`, nodes sorted by `(level, first key)` so key locality = pack locality, single-node read is a ranged GET. Measured motive: 64 packed 1 MiB blobs beat 4096 loose objects 4.7x on a far AWS path. `compact.rs` (`Compactor`, `CompactionPacer`) rewrites partly dead packs. This is a worked example of the pack+index+compaction machinery Lunix will need if it packs 4-64 KiB blocks.

### 2.4 Compression
- Codec registry `crates/store-s3/src/codec.rs`: `CODEC_RAW = 0`, `CODEC_ZSTD = 1`, append-only u16 ids; `CompressionSetting { codec, level: i8 }` parsed from `zstd:7`/`raw`. **No LZ4** (Lunix will want it: add `CODEC_LZ4 = 2`; the registry is explicitly designed for this and "adding a codec is a code change only").
- Framing `crates/store-s3/src/format.rs`: 16-byte header `"CCH1"(4) | version(1)=1 | codec id LE u16 | level i8 | uncompressed_len LE u64`, then payload. `encode_object(data, setting)`, `decode_object(obj)`, and `StreamingDecoder<W>` (decodes into a caller writer while hashing blake3 incrementally; the writer enforces the declared length per `write`, so a bomb arriving in one network read never reaches the sink).
- Guard: if compressed >= original, store raw. Compression is CPU-bound and run off the async workers (`ChunkStore::run_encoder` + `encode_permit`, see 3.4).
- Decompression ceiling `codec::max_decompressed_len()` (default 1 GiB, env `CONSTELLATION_MAX_DECOMPRESSED_BYTES`), `decompress_bounded` (security audit finding 2).

### 2.5 Encryption (`crates/store-s3/src/e2e.rs`)
- Default is *no* client-side encryption (S3 SSE + TLS, "credentials alone suffice", ADR-8). Optional per-filesystem **E2E passphrase mode**, fixed at `fs create`.
- **Key hierarchy**: random 32-byte master key (KMK), wrapped by an Argon2id KEK (defaults m=64 MiB, t=3, p=1; params stored in the `KeyringBlock` so old keyrings keep opening) using XChaCha20-Poly1305 with AAD `"keyring-master"`; the wrapped block lives inside `meta.json` (no separate keyring object). Everything else is **derived, never stored**: `derive_from_master(master, purpose) = blake3::keyed_hash(master, "constellation/e2e/v1/" || purpose_tag [|| partition])`. Purposes: addressing key (0x01), gossip seed (0x02), per-partition DEK (0x03 + name). `fs passwd` re-wraps only the KMK (`rewrap_master`), so no data re-encryption and no addressing change. Keys are mlock'd best-effort (`region::lock`) and `Zeroizing`.
- **AEAD**: XChaCha20-Poly1305, **random 24-byte nonce per object** (`rand::random()`), envelope = `version(1) | nonce(24) | ciphertext+tag`, AAD supplied by the caller = the object identity (for chunks, the chunk hash; so ciphertext cannot be relocated to another key). `encrypt_object(key, aad, plaintext)` / `decrypt_object`. Chunk path in `store.rs::put_chunk_mode`: `encode_object` (compress) then `encrypt_object(&keys.dek("p0"), &hash.0, ...)`.
- **Dedup vs encryption**: *not convergent encryption*. Dedup works because the **object name** is the **keyed** blake3 of the plaintext (same plaintext + same FS key = same name); the ciphertext itself is randomized, so the first uploader's bytes win via create-if-absent and others just skip. The provider cannot test "does this bucket contain file X" because names are keyed hashes (this is the confirmation-of-file leak that plain convergent encryption/plain hashes have, DESIGN.md section 8). Dedup is therefore per-filesystem/per-key only, never cross-tenant. Metadata (pack frames, blobs, commits) is AEAD-sealed per kind (`TreeSealing::from_keys`, one derived key per object kind, object identity as AAD).
- Whole-object AEAD means the full plaintext of one chunk is materialised at decrypt time; `decode_gate.rs` (`DecodeGate`, `Priority::{Demand,Background}`) caps concurrent decrypts to bound RSS, with demand reads cutting ahead of prefetch and a starvation timeout. A Lunix design with 64 KiB-1 MiB chunks has far less of this problem.
- Gaps to know about: no per-chunk key rotation; no streaming/chunked AEAD (STREAM construction) because chunk size is bounded; authenticated `meta.json` was added late (audit finding 12: unauthenticated `meta.json` allowed a silent downgrade of E2E to plaintext, fixed via the local E2E pin `cli::e2e_pin`, `E2eKeys::pin_fingerprint`).

### 2.6 Zero detection
None. Grep for all-zero/is_zero in `fs-core`, `store-s3`, `engine` finds only test fixtures and hole punching. Sparse files are represented by *absent* entries in `SparseChunks = BTreeMap<u64, ChunkHash>` (`manifest.rs`; `Manifest::from_sparse_chunks`), populated through `fallocate(PUNCH_HOLE)` handling. Lunix must add a zero check on the write path (and TRIM/discard/WRITE_ZEROES -> hole entries); the manifest's "missing index = hole" convention is a good reuse of the idea. Note the data-plane tests already confirm 8 MiB of zeros compresses to a tiny object (`format.rs` test), so zero chunks are *cheap* but not free: still one PUT + one hash per chunk, which Lunix should avoid.

## 3. S3 store layer (`crates/store-s3`)

### 3.1 Client library and config
- `object_store 0.14` with `AmazonS3Builder` built in `aws_auth.rs`: `amazon_s3_builder[_resolved]`, `configure_s3_client`. Credentials via the AWS SDK chain (env, profiles, SSO, IMDS, web identity, credentials-process) mapped to an `object_store` credential provider; endpoint from `AWS_ENDPOINT_URL_S3` / profile `endpoint_url` / `services` stanza (needed for B2 and similar). Refreshable-credential flag feeds the retry classifier (`classify::set_refreshable_credentials`).
- `configure_s3_client`: `with_conditional_put(S3ConditionalPut::ETagMatch)`, retry budget **30 s total** (`CONSTELLATION_S3_RETRY_TIMEOUT_MS`, `CONSTELLATION_S3_MAX_RETRIES`) instead of object_store's 180 s default (EC2 finding 1: 3 minutes of retries behind a FUSE op), and a `RedactingConnector` that strips S3 error bodies down to the error code (auth failures echo `StringToSign`/`CanonicalRequest`, which otherwise leak into logs and kubelet events).
- HTTP/1.1 reqwest connector; uploadbench notes "HTTP/1.1 `object_store` PUTs".

### 3.2 Conditional writes and the commit protocol
- Required S3 features (hard constraint 1, ADR-27): GET, PUT, LIST, DELETE, `If-None-Match: *` and `If-Match` on PUT. Nothing AWS-only (no Express One Zone, no conditional DELETE, no RenameObject). `fs create` preflights and refuses a backend without create-if-absent (`ChunkStore::preflight`, `probe_conditional_writes`). One bucket, one prefix per filesystem; no cross-bucket quorum (relevant: Lunix's multi-backend mirroring is a *new* problem Constellation explicitly declined).
- `cas.rs`: `put_conditional(store, path, body, PutMode, Verify)` returns `CasPut::{Won(UpdateVersion), Lost, Missing}`. Status table it implements: 412 on create = key exists (lost race); 409 = another conditional write in flight, **retry the same attempt** (backoff `BUSY_BACKOFF` doubling to `BUSY_BACKOFF_MAX`); 404 on If-Match = object gone (re-read). `object_store` maps 409 on create to `AlreadyExists` too, so `classify` inspects the wrapped error text (documented limitation, fallback is still correct, one GET slower). **`Verify::Body`**: after a 412/404, GET the object and compare bytes to what we tried to write, to catch the case where our own retried/timed-out PUT had already landed (object_store retries conditional PUTs on 5xx). Requires every CAS body to be unique per writer/attempt (lease holder+expiry, node id, commit author). Torn-read re-reads for emulators whose GET is not atomic against PUT.
- Content-addressed create: `cas::create_content_addressed` (409 retried, never a dedup hit; 412 = dedup hit).
- **Lease** (`lease.rs`): `leases/<part>.json`, create (If-None-Match) to claim, swap (If-Match) to renew/release/take over; `Lease { holder, epoch, expires, ... }`, **epoch bumps on every holder change and rides on every log segment/commit** so a deposed holder's late flush is recognisable. TTL default 60 s (`CONSTELLATION_LEASE_TTL_MS`). Mutual exclusion needs no clock agreement; clocks only affect liveness (when to try a takeover). `LeaseMode::SingleWriter` degrades swaps to unconditional PUT for backends with no `If-Match` (local FS object store). DESIGN.md section 5 and ADR-12/22/33 add continuation epochs, seals and Vertical-Paxos-style groups, which are multi-writer concerns Lunix (single writer) does **not** need.
- **Commit chain** (`commits.rs`): `commits/<seq:016x>` created with If-None-Match, immutable, each a *complete state* (names a root hash + the packs it introduced, `CommitPayload`, `Intent`). `CommitChain::publish` refuses to run while the node cache holds unpacked nodes and verifies every named pack exists before the CAS. Invariant: *every node and pack a commit names is durable before the commit object is created*; the crash outcomes are exactly {orphans before the CAS, complete commit after}. Test `no_commit_ever_names_a_missing_node` injects a failure between pack PUT and CAS. Deleting old commits costs only time-travel depth. A reader's view is a version, not a log prefix. `get_run`/`discover_head`: GET-next tailing with LIST only when catching up.
- Log segments (`log.rs`, `log/p0/<seq>.zst`) with slot-CAS fencing are the older mechanism; the commit chain replaced checkpoint+log replay (plan 28).

### 3.3 Multipart, large objects
No multipart upload is used anywhere in production code (only a pass-through in a test wrapper, `crates/engine/src/mtree_publish.rs`). Chunks are single PUTs (at most 64 MiB). Lunix with MiB-scale objects can do the same; multipart would only matter for large pack objects.

### 3.4 Retry, backoff, concurrency, hedging
- Layered retries: `object_store` retry (30 s cap) inside; outer callers have own loops (fsync "hard mount" semantics: `classify.rs` `ErrorClass::{Transient, Permanent}`; the default for unrecognised errors is Transient, because waiting is safe for durability and EIO is not; permanent = AccessDenied with valid creds, NoSuchBucket, malformed, disabled KMS key; `ExpiredToken` transient only if credentials are refreshable). `load_fs_waiting` backs off 250 ms doubling to 5 s alternating plain and ranged GETs to survive inconsistent reads.
- **`crates/upload-concurrency`** (649 lines, depends only on tokio): `AdaptiveConcurrency` (pure policy: slow-start doubling until a probe fails, then binary search of the knee; 3 s min/8 s max observation windows, 5% gain / 5% regression thresholds, two-window confirmation, failures coalesced into one backoff, periodic re-probe) and `ConcurrencyGate` (elastic semaphore; shrink never preempts in-flight work; `acquire`/`OwnedConcurrencyPermit`). Hard cap 128 in `engine/src/upload.rs` (`UPLOAD_CONCURRENCY_HARD_MAX`); `ConcurrencyGate` also bounds pending-upload memory. Measured in `bench/uploadbench/RESULTS.md`: EU home -> us-west-2 saturates ~25-30 MiB/s around N=64-128 (N=256 hits the 30 s timeout cliff, 37% errors); same-region 2 vCPU EC2 reaches 770 MiB/s at N=16, ~2.4 GB/s plateau at N=64; untuned AIMD stalled at ~14, tuned version gets 84.5 MiB/s on a synthetic 1 Gbps/150 ms/SlowDown-storm model (fixed N=4: 51; PID/Vegas: 29 and never recovers). **This crate is directly usable by Lunix as-is.**
- **Hedging** lives in `crates/engine/src/sources.rs` (`Selector::pick`, `hedge_deadline_ms`) and is *source selection across S3 and P2P peers*: EWMA of TTFB and goodput per source, ETA = TTFB + size/goodput + penalties, 20% hysteresis, at most one hedge per fetch, fired after predicted P95 first byte plus body time times `HEDGE_SLACK` 1.5. It is not S3-GET-vs-S3-GET hedging, but the same scoring generalises to "which of N mirrored backends serves a read" for Lunix. It depends on `constellation_net::PathKind`, so it must be extracted.
- Dedup upload ladder (`ChunkStore::put_chunk_mode`, `ChunkPutMode::{Create, Probe, Overwrite}`): create-if-absent (1 RTT) or HEAD first when a hint says the chunk likely exists (chunks under `CONSTELLATION_PROBE_MIN_BYTES` 256 KiB never probe on a guess). `object_store` does not send `Expect: 100-continue`, so a create hit still transmits the body. The GC "condemned" pointer is read only after a dedup hit (`gc.rs`, `CondemnedView::verdict` -> `DedupVerdict::{Sound, Condemned, Unordered}`); see 6.

### 3.5 Provider quirks handled
- Conditional-write status codes per provider (`probe.rs` table): create over existing key: 412 (AWS, MinIO, R2), 304 (some older gateways); If-Match stale etag: 412; If-Match on missing key: 404 (AWS) vs 412 (R2, MinIO); 8 concurrent creates/swaps of one key: exactly one winner (two winners = `violation`, doctor fails); 409 under concurrent conditional writes.
- OVH (Milan bucket, EC2 us-west-2 clients; `crates/harness/src/scenarios/ovh.rs`): ~210 ms p50 on S3-polling paths vs 28-34 ms on AWS (DECISIONS.md section ADR-20 area); cto strict cost 10.19 ms vs 1.07 ms warm stat on OVH vs AWS. `bench/s3_assumptions.py` has `S3_ENDPOINT`, `S3_ADDRESSING=path|virtual` (OVH/MinIO usually want path-style). A conditional PUT takes 28-190 ms depending on distance (ADR-28).
- Backends named as exercised: AWS S3, MinIO, R2, OVH, and a test backend `floci`; `docs/how-to-guides/operations/use-custom-s3-endpoint.md` covers custom endpoints; Backblaze B2 appears in the endpoint-resolution comments. Bucket versioning detected from the probe PUT's `x-amz-version-id` (no extra request) and reported (GC deletes then leave noncurrent versions until a lifecycle rule expires them).
- Objects fetched from a bucket are untrusted: any decoder must tolerate "any bytes at all" (audit).

### 3.6 `doctor`
`constellation doctor` = `engine/src/doctor.rs` (printing, fatal decisions) over `store-s3::probe::probe_cas_semantics` (`CasProbeReport`, `CasProbe{name, observed, known, violation}`, `Versioning`) and `ChunkStore::preflight()` (list of `PreflightCheck`: bucket reachability, write permission, GET/PUT/DELETE round trip, "etag CAS (If-Match)", create-if-absent). Unknown answers warn with "please report the provider and this line"; two winners fail. Lunix should copy this verbatim in concept and extend it with: ranged GET, multipart if used, HEAD consistency after PUT, LIST consistency, max object size, clock skew (Date header vs local), and cross-backend latency.

## 4. Local cache and local state

### 4.1 `DiskCache` (`crates/fs-core/src/cache.rs`, 2.5k lines)
- Layout `<root>/<aa>/<bb>/<hex>`, decompressed by default for `pread` speed (knob), accounting in memory rebuilt by a directory scan at startup (`rescan` marks everything Clean; the durable "owes S3" truth is the metadata journal's `pending_upload` table, not the cache).
- States `ChunkState::{Clean, Pinned, Dirty}`; eviction = LRU by a logical clock over Clean only (`prune_to(target_used)`, `clean_by_recency`); pressure order: evict clean -> throttle writes -> ENOSPC; "reserve-before-accept" ENOSPC discipline.
- Crash consistency: `begin_spill` -> `SpillFile` (temp file), write, `sync_data()` (fdatasync) -> `commit_spill` renames under the state lock; files appear only by rename under the lock, and eviction unlinks only if the hash has not been re-inserted (`unlink_absent`). Hash verification policy `CacheVerify::{Admit, Always}`: every chunk is hashed once as it streams in; reads re-hash only files found by the startup scan (not hashed by this process). Optional in-memory verified tier `memcache.rs` (`MemCache`, `get_shared` coalesces concurrent loads).
- `DiskCache::pin_open` / `OpenPin`: open-file refcount makes a clean chunk unevictable; not relevant to Lunix.
- Limits for a block device: single global `Mutex` state; whole-chunk granularity (a 4 KiB write to a cached chunk is a full-chunk RMW); one file per chunk (inode and syscall overhead at 64 KiB chunks and 100M+ entries); no write-back journal of sub-chunk dirty ranges (that is `staging.rs` + `pending_upload` in `meta`).

### 4.2 Staging and write-back (`crates/engine/src/staging.rs`, `writeback.rs`, `upload.rs`)
Interesting for Lunix's write-back design: sparse per-file staging with **chunk-sized slots** (not mirrored at file offset) after measuring that punching holes in a mirrored staging file costs ~170 ms per 4 MiB chunk on btrfs+zstd (DESIGN.md section 3 "Staging slots"; 3-8 ms btrfs/xfs, 0.1 ms ext4/tmpfs). `StagingBudget` (hierarchical byte budget with `reserve`/`release`/`wait_below`), `DirtyRuns` (run-length dirty chunk set), `--write-mode through|back` with `fsync` always acting as `through`. **Invariant: "the log never names a chunk S3 lacks"** (chunks uploaded before the manifest ships). The local FS-hole-punching lesson is highly relevant to Lunix (local FS as store): avoid `FALLOC_FL_PUNCH_HOLE` on the hot path.

### 4.3 Metadata store: fjall
`crates/meta` uses **fjall 3** (LSM), vendored 3.1.10 + `lsm-tree` with patches (shutdown deadlock in `DatabaseInner::drop`; compaction/flush holding the tree version lock across disk I/O). Plan 29 replaced SQLite (ADR-9 benchmark at 20.2M records: SQLite 578K dentry lookups/s 1.60 GB; LMDB 787K/s 2.5 GB; redb 59K/s 4.3 GB; fjall most compact 0.66 GB and fastest load but 4K/s untuned point reads). Writes are synchronous; commit reaches OS buffers, "state that safety rests on is synced before it is acted on". `store_io::store_call` moves the runtime worker's other tasks away while a blocking store call waits. Bench files: `bench/dbbench`, `bench/enginebench`, `bench/time-{fjall,lmdb,redb,sqlite}.txt`. `meta` is 72k lines of FS semantics (inodes, journal, speculation); **don't reuse `meta`**. The design lessons (keyspaces for pending-upload queue written in the same transaction as the intent; periodic compaction of churn-heavy keyspaces) transfer.

### 4.4 Process-level crash/safety primitives (`crates/platform`)
`lock.rs` (`flock` guards, `daemon.lock`), ADR-29 (state dir takeover only from a process the kernel already killed, classified from `/proc`), `fs.rs` (`FsPrimitives`: `punch_hole`, preallocation, fsync strength), `secrets.rs`, `forbid_core_dumps`, `clock.rs` (protocol clock with fault injection), `drain.rs`/`lifecycle.rs`. Linux build pulls `zbus`/logind. Useful candidates to extract: `lock`, `fs` primitives, `forbid_core_dumps`, ADR-29 logic (a stale-daemon lock is exactly a Lunix problem too: the ublk device holds the kernel object).

## 5. Metadata structures

### 5.1 `mtree` (`crates/mtree`)
- A **canonical prolly tree** (Merkle search tree) over opaque byte keys/values, pure and synchronous: no S3, tokio, fs, or clock. A node ends after key `k` when the level-th u32 window of `hash(k)` < `u32::MAX / TARGET_ENTRIES`, with `MIN_ENTRIES=1` (effectively none) and `MAX_ENTRIES=256` clamps. The boundary depends only on the key, so **tree shape and root hash are a pure function of the key set** (insertion order irrelevant; incremental `Tree::apply` byte-identical to `Tree::build`).
- API: `Tree::{new, build, empty, apply, ...}`, `Cursor`, diff, merge-by-delta with exact conflict set, `Census`; `NodeStore` trait (`get(&NodeHash)`, `put(hash, level, bytes)`) with `MemoryNodeStore`; `Hasher::{Plain, Keyed}` (keyed hashing also governs the boundary function, so a provider cannot compute tree shape from guessed keys); `Agg` aggregates at interior nodes (count, bytes, mtime) via a `fn` projection `LeafAgg`. A snapshot *is* a root hash; fsck = recompute root; `diff` cost O(difference).
- `keys.rs`/`record.rs` (inode/dentry/xattr key encodings) are FS-specific and are not needed; **core is reusable for an LBA -> chunk-hash map** with key = big-endian LBA (or chunk index) and value = 32-byte hash (+ flags). Note nodes are ~9.35 KiB at level 0 with 117 entries mean (`bench/prollybench/RESULTS.md`): for a 1 TiB device at 64 KiB chunks that is ~16.8M keys, 4 levels, ~150 MB of leaves before zstd. Dirty-block updates rewrite one root path (4 nodes), and sequential LBA keys give the best locality (the "clustered" case: 68-150 B/op zstd vs ~1.5-3.3x a plain log); random LBA updates are the "scattered" worst case (thousands of bytes/op, 6.7-24.8 KB/op on a 23.8M-key tree in prollybench's chmod test) so Lunix would want to batch many blocks per commit (async mode does this naturally).
- Cost data (prollybench, 32 cores, 35.8M keys): bulk build 2.13M keys/s; 4 levels; interior total 19.75 MiB, leaves 2.73 GiB (zstd ~43%); a one-key diff of the 35.8M-key tree costs 20 node reads.
- Packaging for S3 (`store-s3/src/packs.rs`, `node_cache.rs`, `blobs.rs`, `mark.rs` reachability walk, `compact.rs`) all sits in store-s3 and is entangled with FS record types.

### 5.2 Manifests (`crates/fs-core/src/manifest.rs`)
Typed entries (`ENTRY_INLINE=0`, `ENTRY_MANIFEST=1` spilled chunk list as a chunk, reserved `SLICE_OVERLAY=2`, `PACK=3`, `CDC=4`), inline up to 8 chunks, `encode_chunk_list`/`decode_chunk_list` (bounded decode after audit finding 1). The reserved `slice-overlay` (append small overwrites as (offset, bytes) deltas) and `pack` entries are the same ideas Lunix needs for small random writes; Constellation deferred them, so there is no code to reuse.

### 5.3 Snapshots
FS snapshots are git-style tree objects (`snaps/<id>.json` = {name, path, root hash}) and GC roots (`crates/store-s3/src/snapshot.rs`, `SnapshotStore`, `snapshot_id`, `SnapshotTreeRoot`); `snapsched.rs` + `crates/meta` snapshot policies (plan 32). For Lunix, a volume snapshot = a commit/root hash, so the machinery collapses to "keep this commit as a GC root".

## 6. GC, fsck, writer fencing

- **Bucket GC** (`crates/store-s3/src/gc.rs`, `mark.rs`, `compact.rs`; `crates/engine/src/gc.rs`, `mtree_gc.rs`; DESIGN.md section 14): one node at a time under the `leases/_gc.json` singleton lease (renewed every third of TTL and every 64 deletes; every destructive step fenced on a CAS of the lease etag, never on the round's clock). LIST-based orphan pass over `chunks/`; candidate = last written more than `gc.horizon` ago (7 days default) and unprotected (no live manifest, snapshot tree, hold). **Condemn-wait-recheck**: CAS-publish the candidates as `gc/condemned.json`, wait a full lease TTL, re-tail to head and re-check liveness before deleting. Defense in depth against delete-vs-dedup (a writer committing a manifest that references an existing chunk it did not upload): horizon; condemned-pointer handshake read only after a dedup hit; HEAD-before-DELETE comparing `Last-Modified` (portable S3 has no conditional DELETE, so a residual gap remains and is documented); open-handle holds. Every deletion journaled with evidence under `gc/journal/`; `gc verify` runs mark without sweep.
- Directly relevant to Lunix because dedup + GC across multiple writers/backends is the hard part; with a single writer Lunix can simplify (the writer owns the dedup decision and can maintain a refcount/mark set, no condemned-pointer handshake needed except for racing against its own pending commits and for a second node mounting from a snapshot).
- **fsck**: `crates/engine/src/fsck.rs` (`FsckReport`, `FsckIssue{class,key,detail,repaired,unrepairable}`, exit codes 0 clean/1 issues/2 repaired/3 unrepairable). Detection non-destructive; repair only unambiguous actions; missing content with no cache copy reported as loss, never converted into a shorter manifest. A `mtree` fsck is "recompute root hash".
- **Fencing/epochs**: lease epoch (see 3.2) rides on every segment/commit; ADR-12 "safety never depends on failure detection" - timeouts only decide *when* to try, a CAS decides *whether*. For a single-writer Lunix this reduces to: CAS-create next commit with `prev=seq`, plus lease object with holder id/epoch to prevent two daemons mounting the same volume (clean handoff when a pod moves). Take the lease TTL + renewal + "stop writing when a renewal is refused or the local lease margin is exceeded" logic from `lease.rs` and the fenced-GC pattern.
- Leaseless optimistic commits were considered and deferred (ADR-28) because a conditional PUT takes 28-190 ms; for a single-writer volume the lease is cheap and the right call.

## 7. Async runtime and IO model; benchmarks

- tokio multi-thread everywhere (`tokio` features `rt-multi-thread`, `fs`, `io-util`, `sync`, `time`, `signal`, `net`). CPU work goes elsewhere: zstd and AEAD run on blocking pools gated by an encode permit (`ChunkStore::encode_permit`, `run_encoder`), GC mark/compaction on private rayon pools (`crates/store-s3/src/parallel.rs`, capped by `CONSTELLATION_GC_THREADS`; rationale: a multi-second zstd burst on a runtime worker starves FUSE requests). Synchronous store calls go through `store_io::store_call` (worker hand-off). FUSE threads, fsync waiters and the authority core run on their own threads. Logging never blocks a daemon thread (ADR-32).
- io_uring is used only for the **FUSE-over-io_uring transport** (kernel >= 6.14) in the forked `fuser` and `crates/engine/src/view/*` (zero-copy reads need kernel >= 7.3 `READ_FIXED`). **No ublk, no io_uring file or network I/O** in the workspace. Lunix is on Linux 7.0.
- Benchmark numbers available in `bench/`:
  - `bench/fuse-read-path/RESULTS.md` (2026-09-30): FUSE-over-io_uring `rand4k-8j-dio` 1,510k vs 464k IOPS (3.25x) at 0.78 vs 3.71 daemon CPU s/GiB, p99 8.8 vs 36 us; `rand4k-1j-dio` 280k vs 122k IOPS (2.3x); FUSE passthrough `seq1` 30.8 GB/s (4.6x); memcache tier 2.1-2.2x on dio/small files; splice and vmsplice rejected.
  - `bench/fuse-uring-handover/RESULTS.md`: once a FUSE-over-io_uring ring is ready the connection never goes back to `/dev/fuse`; requests in A's ring entries are lost when A's ring goes away, on kernels 6.17, 7.0, 7.3-rc4. Lesson for Lunix: **a ublk daemon restart/upgrade handover must be designed around ublk's own recovery (`UBLK_F_USER_RECOVERY*`), not assumed lossless.**
  - `bench/uploadbench/RESULTS.md` (above), `bench/remote/RESULTS.md` (4x EC2 8 vCPU, 0.5 ms RTT, plain FS: 1 node `through` small file write 20-270 ops/s vs `back` 5.7k ops/s; sequential 200 MiB/thread write 515-551 MB/s but cold cross-node read only 57-85 MB/s per node), `bench/prollybench`, `bench/dbbench`, `bench/enginebench`, `bench/dirsplit`, `bench/csi-metadata`, `bench/commit-rule`.
  - Hashing: blake3 is described as multi-GB/s per core and never the bottleneck (DESIGN.md section 3); I found no dedicated hash micro-benchmark in `bench/`.

## 8. CSI driver (`crates/csi`)

- Structure: `main.rs` (flags `--controller` / `--node`), `identity.rs`, `controller.rs` + `controller/snapshots.rs`, `node/{mod,mounter,engines,handoff,rollout,gc,state}.rs`, `engine_pods.rs` (+ `engine_pods/controller_pods.rs`, ~6.6k lines: starts one `constellation serve` pod per pool filesystem per node via `kube` 4.2 / `k8s-openapi` v1_36), `credentials.rs`, `params.rs`, `purge.rs`, `volume_id.rs`, `control_client{,/socket,/fake}.rs`. Stack: `tonic 0.14`, `prost 0.14`, `kube 4.2`; `build.rs` compiles `proto/csi.proto` (CSI spec **v1.13.0**, `proto/VERSION`) with `protoc-bin-vendored`. Helm chart under `deploy/helm/constellation-csi`; guide `docs/how-to-guides/kubernetes-csi.md` (K8s >= 1.30 for ValidatingAdmissionPolicies; only the node plugin is privileged; driver name `constellation.csi.replicix.com`).
- Design points worth copying: (1) **`volume_id` codec** `v1/pool/<shard>/<fs-uuid>/volumes/<name>`, `v1/dedicated/<fs-uuid>/`, unversioned static `<fs-uuid>/<path>`; versioned header so a later codec cannot misread old ids; every RPC resolves the target from `volume_id` alone, no registry/CRD. (2) **Credentials never in pod spec/env/image/hostPath**: engine pods start `--await-unlock`, accept `fs.unlock` over a control socket from `req.secrets` (or a watched Secret for `credentialSource: refreshing`, with list+watch re-list backoff 1 s -> 30 s), held in an `EphemeralSecretStore`, rotated without remount; plugins run with core dumps off. (4) Test seams: `FakeMounter`, `control_client/fake.rs`, `--in-memory-backend`, `csi-sanity`, kind-based scenarios.
- Not applicable to Lunix: pool/shard filesystem layouts, snapshot hold plans, RWX/cto semantics, FUSE fd handover to engine pods. **Constellation's CSI does not offer block volumes** (plan 37: "a block-storage RWO mental model" is explicitly not what it is; fixed-size block pool "not implemented"). Lunix's CSI needs `volumeMode: Block` (`NodePublishVolume` bind-mount of `/dev/ublkbN` or a symlink/device node into the pod's `volumeDevices` path) and `Filesystem` mode (mkfs + mount via `NodeStageVolume`), `ControllerExpandVolume`/`NodeExpandVolume` for grow, and attach semantics `SINGLE_NODE_WRITER` (RWO) with lease-based fencing rather than the cluster's FUSE sessions. There is no shared Rust CSI crate with the spec bindings; Lunix could extract `identity`, `volume_id`, `credentials` (Secret watch), `params`, and the proto build into a `replicix-csi-common` crate, but the controller/node logic must be written fresh.
- Metadata bench: `bench/csi-metadata/results` (grid 1/4/16/64/256 parallelism; CreateVolume sequences ~1.2-1.4k/s per pool FS per `params.rs` comment) is Constellation-specific.

## 9. Security audit highlights relevant to a block device (`docs/security-audit-2026-09.md`)

Threat model: anyone with S3 write access can plant crafted objects, so every decoder of bucket bytes is reachable by arbitrary input; peers semi-trusted; localhost API treated as attackable via DNS rebinding. 14 libFuzzer targets in `fuzz/fuzz_targets/` (`store_object.rs`, `fscore_manifest.rs`, `fscore_tree.rs`, `mtree_node.rs`, ...), run with rss/malloc limits so unbounded allocation is a finding. Directly transferable:
1. Unbounded allocation from a decoded count: never `Vec::with_capacity(count)` from an untrusted `u32`; bound by remaining input / min entry size (finding 1; uncatchable abort). Applies to Lunix block-map nodes, commit records, chunk lists.
2. zstd bombs: cap output at the declared length, cap the declared length at a ceiling, enforce per write inside the sink writer (finding 2).
3. Authenticate the root-of-trust metadata (finding 12: unauthenticated `meta.json` allowed silent E2E downgrade; fix = local pin of the master-key fingerprint). For Lunix: AEAD-seal and bind the volume config and commit objects to the key; refuse a plaintext commit on an encrypted volume.
4. Validate sizes read from the bucket (finding 7: `meta.json` chunk size trusted on load, HIGH). For a block device a hostile `chunk_size`/`volume_size` could drive allocations or bogus device geometry.
5. Bucket-writable fields with arithmetic (finding 11: unchecked epoch arithmetic): use checked math on epoch/sequence/size fields.
6. Registry/lease records must trust their *key*, not their body (finding 10).
7. Redact S3 error bodies (RedactingConnector) before they reach logs/events.
8. Mutex-poison cascade (finding 5): a panic under a shard lock must not wedge every later request; critical for a block device where a stuck daemon hangs every process doing I/O to the device.
9. The HTTP control API on loopback needs Host/Origin guards (finding 3); Lunix's control socket should be a Unix socket with peer-credential checks instead.

## Recommendations for Lunix

1. **Create a shared workspace/repo for extracted crates** (e.g. `replicix-core`) instead of Lunix depending on Constellation's workspace, and make Constellation depend on it in turn (the user's memory notes say Constellation is modifiable). Candidate crates, in order of value/cost:
   - `upload-concurrency` as-is (move or git-dep, zero code change).
   - `objcas` from `store-s3`: `cas.rs`, `classify.rs`, `probe.rs`, `aws_auth.rs` (with `RedactingConnector`), `layout` helpers, `lease.rs` (de-couple the clock), the `PreflightCheck` machinery. This is the S3 correctness core that Lunix needs for each mirrored backend.
   - `chunkfmt`: `ChunkHash`, `codec.rs` + `format.rs` (+ new LZ4 codec), `e2e.rs` encrypt/decrypt/derive, `decode_gate`. Keep the `CCH1` header byte-compatible; add a `CCH1` codec id for LZ4 (2) rather than a new magic.
   - `merkle-map` from `mtree` core, with `NodeStore` over a pack store. Optional for v1 (see 3 below).
   - `platform-lite`: `lock`, `fs` (hole punch, fsync strength), `forbid_core_dumps`, ADR-29 stale-lock takeover.
2. **Adopt the chunk object format and addressing as-is**, with the modifications a block device needs: (a) smaller default chunk (suggest 64 KiB-256 KiB aligned to the filesystem block use, power of two up to 4 MiB; benchmark RMW amplification vs request count; Constellation's own trade-off note: larger = fewer requests, smaller = less RMW and re-upload); (b) all-zero chunk -> sentinel in the map, never hashed/stored (use blake3 of zeros precomputed as constant if a hash is needed); (c) pack small chunks into larger S3 objects (segments) with an index sibling object like `packs/<hash>.idx`, reusing the pack+index+compaction design from `packs.rs`/`compact.rs` instead of the one-object-per-chunk layout, because at 64 KiB a 1 TiB volume is 16.8M objects, which makes LIST/GC/cost untenable (ADR-11's own argument for packfiles). Keep chunks individually addressed inside packs so dedup is unaffected.
3. **Use the commit-chain + root-hash model for the crash-consistent S3 image**: map (prolly tree or simpler) nodes and data segments uploaded first, then `commits/<seq>` CAS-created (`If-None-Match`) containing {root hash, size, epoch, prev}. The mountable state on S3 is always the latest commit; async mode just changes how often a commit is cut; sync mode cuts one per FLUSH (but batch to avoid one conditional PUT, 28-190 ms, per FLUSH where possible, or use group commit). Single writer means the lease only guards against two daemons; `Verify::Body` read-back, 409 handling and the doctor probes make the CAS robust across providers. Choose between a prolly tree (cheap snapshots, O(diff) sync to a new backend, mirror verification by comparing root hashes) and a flat per-extent table (simpler, cache friendly, O(volume) commit size) by measuring commit cost at expected volume sizes; prollybench shows clustered updates are cheap and scattered updates expensive, and block workloads are often scattered (journals + metadata hot spots + random DB pages) before batching.
4. **Multi-backend mirroring is net-new design**: Constellation rejected multi-bucket (ADR-27). Reuse per-backend `ChunkStore`/CAS code, `Selector`'s EWMA/hedge scoring for read source choice, and the fact that content-addressed immutable objects and root-hash commits make "add a backend" = copy missing objects (diff by `mtree` or by listing packs) then CAS-create the head commit on the new bucket; "remove a backend" = stop issuing writes, wait for in-flight, drop. The root hash is identical on both backends if hashing is backend-independent, which makes verification trivial.
5. **Encryption**: reuse the KMK/Argon2id/derive-by-purpose scheme and XChaCha20-Poly1305 with random nonce and hash-as-AAD; keep keyed-blake3 addressing for the encrypted mode and plain blake3 otherwise. Decide early whether Lunix offers a plain-hash mode at all (provider confirmation-of-file leak only matters if the provider is an adversary; for block volumes of private filesystems, the leak is "provider can test whether a known block, e.g. a zero block or a common OS file block, exists", which is a real concern for stock images, so default encrypted volumes to keyed addressing). Pin the master-key fingerprint locally to stop the `meta.json` downgrade class.
6. **Retry and failure semantics**: adopt `classify.rs`'s transient/permanent split and "hard mount" behaviour for FLUSH in sync mode (retry forever on transient, EIO on permanent; user-configurable timeout), but set `object_store`'s retry cap far below 180 s as Constellation did (30 s) because a ublk request is blocked behind it. Add Lunix-specific ublk timeout handling: ublk has per-queue request timeouts; do not let an S3 retry loop exceed them without an explicit decision (EIO vs keep waiting).
7. **Local cache**: copy the `DiskCache` *state machine* (Clean/Pinned/Dirty, evict clean -> throttle -> ENOSPC, temp+fdatasync+rename, rescan on start, hash-once verification policy) but do not inherit file-per-chunk or the global mutex. For Lunix a log-structured local store (append segments + in-memory index, sub-chunk dirty ranges, io_uring fixed-file I/O) will fit the "local FS is the store" and free-space-floor requirements better; the local free-space floor maps cleanly onto `StagingBudget` and the existing throttle-before-ENOSPC ladder. Avoid hole punching on the hot path (the btrfs+zstd 170 ms/4 MiB finding).
8. **GC**: with one writer, simplify: reference-count or mark from retained commits (the tree walk in `mark.rs`), delete only unreferenced objects older than a horizon, and keep the fenced-lease + journaled-evidence + `gc verify` dry-run pattern. If two Lunix instances can ever share a bucket (cloned volumes from one snapshot), keep the condemn-wait-recheck handshake because dedup across volumes reintroduces the delete-vs-dedup race.
9. **Do not copy**: `meta`, `authority`, `engine` sync/forwarding, P2P `net`, coop cache, cto modes, FUSE, `mtree` key/record codecs. Do not adopt fjall by default for a block map (see Open questions).
10. **CSI**: write a new `lunix-csi` crate sharing only extracted helpers (proto build, `volume_id` codec idea, `credentials` Secret watch, `params` strict parsing, Helm privilege split, `Mounter` trait with fake). Design for `volumeMode: Block` first, and for pod-moves-between-regions as `ControllerPublish`/`NodeStage` taking the lease (and, if the old node is gone, waiting out the lease TTL or forcing a takeover with the fencing epoch).
11. **Fuzz and harden from day one**: port the audit's rules as lint-like review points and copy the `fuzz/` layout (structure-aware targets with rss/malloc limits) for every decoder.
12. **Testing assets to borrow**: `crates/store-s3/src/faulty.rs` (fault-injecting object store), `scripted_http.rs` (scripted HTTP for retry/classification tests), `crates/chaos`, `crates/harness` scenario style. These make the CAS protocol testable against an in-memory `ObjectStore` (Constellation notes every protocol can be tested against an in-memory object store).
