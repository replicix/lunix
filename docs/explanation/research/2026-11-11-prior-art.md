# Prior art: block devices / virtual disks on object storage with a local cache

> **Corrections (2026-11-11):** several facts in this note were checked against primary sources in [2026-11-11-fact-check.md](2026-11-11-fact-check.md) (ublk flag kernel versions, provider conditional-write support, prices, latencies, LSVD numbers). Where they disagree, the fact-check wins.

Date: 2026-11-11
Author: research agent (Sonnet)
Question: What existing systems provide block devices or virtual disks backed by object storage with a local cache (research and open source: LSVD, ZeroFS, s3backer, nbdkit, Neon, SlateDB; cloud block: EBS, Ceph RBD, Longhorn, Mayastor, DRBD/Linstor, Portworx, Fly, Archil, Tigris, Lightbits, GCP PD, Azure; Linux caching: dm-cache, dm-writecache, bcache, lvmcache, OpenCAS; image formats: qcow2, VHDX, dm-thin, zvol; dedup stores: VDO, ZFS dedup, restic/borg/kopia)? What did each get right and wrong, where is the gap for Lunix, and which design lessons should Lunix adopt or avoid?

Evidence grading: items marked (V) were verified this session from a primary source (README, kernel docs, search result); items marked (K) are from my prior knowledge and not re-verified; numbers marked (K) should be re-checked before being quoted externally. See "Open questions / UNVERIFIED".

## Summary

- Nobody ships Lunix's exact combination. The closest are LSVD (log-structured, prefix-consistent, local NVMe journal, S3 backend, but research code, no dedup/compression/encryption, no snapshots, Ceph/SPDK-oriented) and ZeroFS (S3-native, NBD+9P+NFS, zstd/lz4 + XChaCha20, SlateDB-style LSM, epoch fencing, but AGPL, filesystem-first, NBD size fixed at creation, no multi-backend mirroring, no ublk, no crash-consistent snapshot story advertised).
- LSVD's central idea is the one to steal: a *log of immutable, sequence-numbered objects* in S3 gives **prefix consistency** for free. If S3 has objects 1..N (no holes), the device image at N is a state the guest could have observed after a crash. This is exactly the "S3 always holds a consistent, mountable, crash-consistent snapshot as of the last sync point" requirement. LSVD's `flush_msec` default is 2 s (V), a good analog of Lunix's bounded-loss async window.
- Content-addressed chunks (Lunix's dedup requirement) and a prefix-consistent log are compatible if the *log* is a log of small metadata records (LBA range -> chunk hash) and chunks are separate immutable objects/packs written before the record that references them. Restic/kopia/borg show the pack + index layout; VDO shows what the dedup index costs.
- VDO is the most relevant local precedent for dedup + compression + zero elimination on a block device. Its lessons (V from kernel docs): 4 KiB blocks, dedup index entries are *hints verified by reading the candidate block*, recency-ordered index (~64M records ≈ 256 GB window by default), 5-byte block-map entries, recovery journal with FUA, early acks (flush/FUA required by apps), compression packing only helps when >=2 compressed blocks fit in a 4K block, zone-per-thread lock-free design, degraded-mode fast recovery. Lunix with larger chunks (16-64 KiB+) is a different point in the design space, but the "hint + verify" and "index memory dominates" lessons transfer. For hash-addressed chunks you can skip verification with a cryptographic hash, but you must still bound index RAM.
- Linux caching layers (dm-cache/writecache/bcache/OpenCAS) all share one design flaw for Lunix's purposes: they cache *a block device*, and their dirty-state metadata is per cache block with weak or no ordering guarantees across blocks. After losing the cache device in writeback mode, the backing device is *not* a consistent image. Lunix must own the cache (as LSVD does) so that write order to S3 is a prefix of guest order.
- Block-over-S3 FUSE/NBD tools (s3backer, nbdkit S3, s3nbd) demonstrate the failure modes: one S3 object per fixed block (or per chunk) with read-modify-write, no ordering, no atomic multi-block writes, listing/metadata overhead, and "consistency" defined per object only. They are fine for backup targets, bad for databases and journaling filesystems after crash.
- Neon's pageserver and SlateDB show the "LSM / layer files on S3 + WAL on fast local/replicated storage" pattern, with a manifest as the single linearization point, and conditional PUT (If-None-Match / CAS manifest) for fencing. Both argue for requiring S3 conditional writes where available and having a fallback (lease object, external lock) where not. ZeroFS requires conditional put (S3 native; others need a Redis helper) (V).
- Cloud block stores (EBS, PD, Azure) all converge on: snapshots stored in object storage as incremental block diffs, restore is lazy (hydrate on demand, with a slow first-read penalty that vendors paper over with "fast snapshot restore"/pre-warming). Lunix's "cold cache at the new region" is exactly EBS lazy-load restore; the mitigation is prefetch ordering (metadata/boot extents first) plus a background hydrate.
- Market gap: a portable, cloud-agnostic, multi-bucket-mirrored, dedup+compressed+encrypted, ublk-native volume with crash-consistent S3 snapshots and CSI integration. Longhorn/Mayastor/Portworx replicate between nodes (not between clouds/regions via object storage); EBS/PD are single-cloud; Archil/Tigris/ZeroFS/JuiceFS are filesystems, not block devices with fsync-correct journaling semantics.
- Biggest pitfalls: (1) unbounded GC/space amplification, (2) index/metadata RAM blowup, (3) read amplification on cold cache, (4) flush semantic lies (acking before durable), (5) metadata checkpoint size at multi-TB scale (LSVD explicitly lists this as a known weakness, V).

## 1. Research and open-source block-on-S3 systems

### 1.1 LSVD (Log-Structured Virtual Disk)

Correction: the paper "Beating the I/O Bottleneck: A Case for Log-Structured Virtual Disks" (Hajkazemi, Aschenbrenner, Abdi, Kaynar, Mossayebzadeh, Krieger, Desnoyers) appeared at **EuroSys 2022** (Rennes, DOI 10.1145/3492321.3524271), not 2024 (V via search). The CCI-MOC `lsvd-rbd` repo references a later ATC 2024 submission (V). So: EuroSys'22 is the design paper; ATC'24 is a follow-up (details UNVERIFIED).

Design (V, from `lsvd-rbd` README): an image `pool/name` has a **superblock object** (size, clone linkage, clean-shutdown info) and numbered **data objects** (`name.00000001`...) containing data plus an LBA list so the log can be replayed. **Checkpoint objects** hold the full LBA->object map, written at shutdown and periodically. Writes first go to a **journal on local NVMe** (write cache), then a translation layer batches them into large objects (**default 8 MB**) and updates the map; reads merge extents from write cache, read cache (typically fetching **64 KB** blocks) and backend; unmapped extents read as zeros. Export is NVMe-oF/TCP via SPDK in the Ceph-oriented prototype.

Consistency (V): **prefix consistency** — if a write is visible after crash, all earlier writes are too; recent writes may be lost. Writes up to 2 MB are atomic; larger writes are split, so a tail can be lost. `flush_msec` (default 2 s) bounds potential loss; `hard_flush` pushes every flush to the backend and "has significant performance cost". After a client crash, missing writes are replayed from the local journal.

GC (V): greedy; cleans objects whose live fraction falls below `gc_threshold`. Steady-state utilization is about halfway between threshold and 100%: threshold 60 gives ~80% utilization (25% space expansion). README recommends <=70. With 8+2 erasure coding and gc=60: 1.56x vs 3x for replication. GC spills to a local temp file with no size limit (TODO in README).

Numbers (V, loosely): ~100K write IOPS against an erasure-coded pool on SATA SSD, 32 OSDs at ~30% backend CPU (Ceph 17.2.0, old Ivy Bridge hosts); the paper's pitch is *more aggregate client IOPS per OSD pool* than RBD, not lower single-disk latency. The paper compares against RBD + bcache writeback; exact speedups were not retrieved (UNVERIFIED; recall (K) of "up to several x on write-heavy workloads" is unconfirmed).

Limitations (V): README says "NOT production-ready"; occasional crashes, some memory leaks; **snapshots not implemented** (clone exists); checkpoints may grow too large for multi-TB volumes and need incremental/split checkpoints; **32-bit sequence numbers** (~3 years at 100K IOPS); fragmented reads are rare but tricky; sync-heavy workloads suffer.

What to take: object log + prefix consistency + local NVMe journal + checkpoint objects + clone-by-superblock-linkage. What to fix: 64-bit sequence numbers, incremental checkpoints, GC bounded and rate-limited, snapshots (trivial in a log: record a sequence number).

### 1.2 ZeroFS (Barre/ZeroFS, Rust)

(V, README) Single userspace process serving NFS, 9P and **NBD** over S3-compatible storage. File contents split into **32 KiB extents** packed into immutable **segment objects up to 256 MiB**; metadata (inodes, dirents, 32-byte pointer per extent) in an **LSM tree stored on the same object store** (SlateDB lineage; README says no external DB needed). Compression zstd (default level 3) or lz4, applied *before* encryption, codec changeable without migration. Encryption: **XChaCha20-Poly1305** per extent, data key wrapped with **Argon2id**. Cache: memory + disk tiers. Fencing: **conditional writes (put-if-not-exists)**; AWS S3 native, other stores need a Redis URL via `conditional_put`. HA: optional leader/standby on the same bucket with synchronous mutation forwarding while connected, falling back to "Solo" with a durability window; takeover uses durable phased claim plus **writer-epoch fencing**. NBD FLUSH/FUA replies are sent only after data is durable (V); NFS buffered writes are reported stable and tested clients don't send COMMIT on fsync, so use 9P for fsync correctness. Testing: pjdfstest (8,662 cases), xfstests, Jepsen (local-fs and HA), deterministic simulation — notable rigor to emulate.

Limitations (V): **AGPLv3 / commercial dual license** (important if Lunix wants to borrow code; read ideas only); NBD device **size fixed at creation** (resize = recreate); no stated dedup (extent-pointer model, not content-addressed, as far as the README shows — UNVERIFIED); kernel-native client is out-of-tree DKMS; archive tiers break it. Performance claims are vendor-stated and unquantified in what I retrieved ("near-raw-S3 throughput on large files", "tens of thousands of requests/s").

Lesson: ZeroFS proves the market wants "S3 as a disk" with strong crypto and conditional-write fencing, and that NBD (not ublk) is the current Rust block interface. It is *filesystem-centric*; block devices are a view of a file, so no block-level snapshots/mirroring semantics.

### 1.3 s3backer, nbdkit S3 plugin, s3nbd, BUSE

- **s3backer** (K; I could not fetch the repo this session): FUSE file presenting a single large file backed by one S3 object per block (default 4 KiB, commonly set 64 KiB-1 MiB), with a RAM block cache, optional on-disk cache file, **MD5 per block** to detect S3's historical eventual consistency (now moot since S3 became strongly consistent in Dec 2020), compression, encryption, zero-block elimination (nonzero detection), and a "ghost" MD5 cache. Works for putting ext4/XFS on S3. Known problems (K): block-granular read-modify-write, no write ordering, so crash leaves arbitrary subset of recent blocks written — fs journal may replay but volume is not a prefix; high request count ($/PUT); listing a huge bucket to detect zero blocks is slow; no snapshots; FUSE overhead; single-writer by convention only. The project's author recommends larger blocks and the filesystem's `-o discard` support.
- **nbdkit S3 plugin / nbdkit generic** (K): nbdkit has plugins for S3-ish storage and filters (cache, cow, retry, offset); a block-over-S3 plugin exists but is minimal; the **cow/cache filters** show a clean layering idea (filter chain) but no durability semantics on cache loss.
- **s3nbd / similar** (K, UNVERIFIED names): small NBD servers writing fixed-size objects; same issues as s3backer.
- **BUSE** (K): userspace block device via NBD socket pair (Linux `nbd` driver). Predecessor of ublk; extra copy and a single socket queue limits throughput (typically tens of K IOPS). Lunix's ublk + io_uring design removes this.
- **JuiceFS / ObjectiveFS** (K): filesystem on S3 with a block format of 4 MiB chunks (JuiceFS: chunk -> slices -> 4 MiB blocks) and an external metadata DB; shows the cost of an external metadata server (Redis/TiKV/SQL) — Lunix should avoid it by keeping metadata in S3 objects.

Takeaway: fixed small block per object is the anti-pattern; use log-structured large objects with an index.

### 1.4 Neon, SlateDB, turbopuffer, WarpStream

- **Neon** (K): Postgres compute separated from storage. **Safekeepers** (Paxos-replicated WAL on local disks) acknowledge commits; **pageserver** ingests WAL into **layer files** (immutable *delta layers* keyed by (page, LSN) ranges and *image layers* of full snapshots) written to S3, with local disk as cache and on-demand download ("lazy" layers). Compaction/GC converts deltas to images; branching is nearly free because layers are immutable and shared by timeline ancestry. Metadata: `index_part.json` per timeline as the linearization point (conditional in later versions; K). Lessons: immutable layered files, image+delta, branching = pointer to ancestor at LSN, remote-storage upload queue that preserves ordering of metadata visibility (index uploaded only after layers durable). Failure: cold-start latency when layers must be fetched; compaction write amp; operational complexity. Lunix analog: LSN = log sequence number; "image layer" = periodic full-extent checkpoint.
- **SlateDB** (K/V partial via ZeroFS): embedded LSM on object storage; WAL objects, SST files, a **manifest** updated via conditional write for fencing (writer epoch); configurable flush interval trades latency vs PUT cost (default ~100 ms, K); cache of blocks/SSTs on local disk. Failure/limits: write latency floor equals S3 PUT latency (tens of ms; S3 Express One Zone ~single-digit ms), write amplification from compaction.
- **turbopuffer / WarpStream** (K): object-storage-native with a stateless or lightly stateful compute tier; WarpStream's agents write directly to S3 (batching across producers to amortise PUT cost) and uses a metadata service for ordering; turbopuffer uses NVMe + RAM cache with S3 as source of truth and highlights **cold vs warm query** gap and tail latency. Lessons: batch to amortise request cost; make cold path explicit and prefetch-friendly; use S3 Express One Zone for low-latency log tail (K, availability by region/provider limited — not portable across vendors).

## 2. Cloud and cluster block storage

- **AWS EBS** (K): replicated within AZ; **snapshots are incremental, stored in S3**, block-granular (changed-block tracking at 512 KiB granularity; K) with snapshots chaining so deletion of one preserves needed blocks. **Restore is lazy**: volume is usable immediately, blocks are pulled from S3 on first access with first-touch latency penalty (AWS advises pre-reading with `fio`/`dd` to "initialize"). **Fast Snapshot Restore (FSR)** pre-hydrates in selected AZs for a fee and a bounded number of volumes/hour credits. **EBS direct APIs** (ListSnapshotBlocks, ListChangedBlocks, GetSnapshotBlock, PutSnapshotBlock; 512 KiB blocks, K) allow reading/writing snapshots from outside, enabling third-party backup. Also Volume Initialization Rate option (K). Lesson: lazy hydrate is accepted by industry; offer an *explicit* hydrate-priority knob.
- **Ceph RBD** (K): image = objects of 4 MiB by default (`rbd_object_size`), striping optional; RADOS replication/EC; **exclusive-lock** feature gives single-writer with cooperative lock handoff; **object-map** and **fast-diff** speed up diffs; **layered clones** (copy-on-read option); snapshots via RADOS snapshots; **journaling** mode for rbd-mirror (write-ahead journal, then replicate) yields crash-consistent async mirroring but halves write performance (K; reported ~2x write penalty); snapshot-based mirroring is cheaper but coarser. Lessons: 4 MiB objects are good for sequential but cause write amplification for small random writes (RMW of 4 MiB object on EC pools); exclusive lock + blocklisting for fencing; journal-based mirroring cost.
- **Longhorn** (K): v1 per-volume engine with N replicas on node-local sparse files (snapshot chain of sparse files, 4 KiB-granular, 'diff disks'), iSCSI frontend, replica rebuild by copying snapshot chain; backups to S3/NFS as **2 MiB blocks** deduplicated by hash with incremental backups (this is a real S3 dedup layout precedent). v2 data engine uses SPDK, needs hugepages/dedicated cores, still maturing (K). Failures: rebuild storms, long chains of snapshots degrade read performance, v1 performance low (iSCSI + Go), restore from S3 is a full copy, not lazy.
- **OpenEBS Mayastor** (K): Rust + SPDK, NVMe-oF, synchronous N-way replication across nodes; very fast (near NVMe) but replication is synchronous and node-local; no object-store tiering; snapshots are via LVS; requires hugepages and isolated cores.
- **LINSTOR/DRBD, Piraeus** (K): DRBD kernel module synchronous replication (protocol C) with bitmap resync and activity-log for fast resync; LINSTOR as orchestrator; Piraeus is the Kubernetes operator. Proven, very low latency, but replicas are node-attached disks in one low-latency network; WAN needs DRBD Proxy (async protocol A, buffer). No object-storage layer.
- **Portworx** (K): proprietary, replicated block with cloud-drive integration, CloudSnap to S3. Heavy, commercial.
- **Fly.io volumes / LiteFS** (K): Fly volumes are node-local NVMe tied to one host and region (no live migration; snapshots daily to object storage, restore creates a new volume); LiteFS is a FUSE layer replicating SQLite pages. Takeaway: users complain that volumes are pinned to a host — a direct validation of Lunix's mobility pitch.
- **Archil** (V via search): "serverless disks" — managed NVMe caching fleet providing read-through and write-back caching to S3 or other data sources; data stored in *native S3 format* (no proprietary block format); per-disk S3 endpoint; strongly read-after-write consistent for connected clients, eventually consistent with the data source (object written directly to S3 can take minutes to appear). Early-access/waitlist status; claims (30x lower latency than S3, ~90% cheaper than EBS) are vendor claims. It is a POSIX filesystem product, not block.
- **Tigris** (K): globally distributed S3-compatible object store with automatic regional replication and caching; relevant as a *backend* for Lunix (global bucket). Details UNVERIFIED.
- **Lightbits** (K): NVMe/TCP disaggregated storage, replication in-cluster, snapshot/clone, low latency (sub-ms); on-prem/cloud software; no S3 tiering for primary.
- **Google Persistent Disk async replication / Hyperdisk** (K): async replication of PD between regions with RPO ~1 min target, secondary is read-restricted until failover (promote); consistency groups for multi-disk crash-consistency; single-cloud. This is the model for "async mode with bounded RPO" in cloud-speak; note the concept of **consistency groups**, relevant if a pod has multiple Lunix volumes.
- **Azure managed disks** (K): ZRS, incremental snapshots (page blob snapshots), cross-region disk restore via snapshot copy; Azure Elastic SAN; Azure "disk bursting". Single-cloud.

Comparison summary: all are either synchronous and local (Mayastor, DRBD, Longhorn) or single-cloud with S3-like snapshots (EBS/PD/Azure). None gives vendor-neutral mirrored object-store backing with live add/remove of backends.

## 3. Linux caching layers

- **dm-cache** (K): metadata device + cache device + origin; policies `smq` (default; stochastic multiqueue, hotspot tracking, replaces mq) and `cleaner` (flush everything to origin); modes writeback, writethrough, passthrough; block size 32 KiB-1 GiB typical 64-256 KiB; dirty bits per cache block in a persistent metadata (superblock + bitset + mapping array); **clean shutdown writes a clean-flag; after unclean shutdown all blocks are treated as dirty-until-proven (since kernel 3.x 'needs_check' semantic)**. In writeback mode, if the cache is lost the origin is inconsistent (blocks written in cache but not yet migrated) — no ordering preserved. Throttles migration bandwidth (`migration_threshold`, default 2048 sectors). Lesson: smq works for read-heavy hot sets; writeback is not crash-consistent across devices.
- **dm-writecache** (K): write-only cache for persistent memory (PMEM, via DAX) or SSD; `high_watermark`/`low_watermark` (percent) control writeback start/stop (defaults ~50%/45%); `writeback_jobs`; `autocommit_blocks`/`autocommit_time` (default 1000 ms) after which writes are committed; flush/FUA honored by committing metadata. Reads not cached (bypass to origin unless in cache). Block size 512 B-4 KiB. Simple and robust; PMEM mode is fastest, SSD mode slower because of metadata writes. Writeback order not guaranteed vs. guest order (origin may be inconsistent after cache loss).
- **bcache** (K): SSD cache with btree index, journal, sequential-IO cutoff (default 4 MiB, bypasses large sequential), writeback modes (`writethrough`, `writeback`, `writeback_percent` default 10, `writeback_delay` 30 s), congestion thresholds. Known weaknesses: complexity, historic data-corruption bugs under certain loads, no cache-device-loss recovery in writeback mode (data lost, backing fs likely corrupt), maintainers few. Used as RBD client cache in LSVD comparison (V).
- **bcachefs** (V via search): removed from mainline in 6.18 after being marked externally maintained in 6.17; shipped as DKMS (bcachefs-tools 1.31.5; supports kernels 6.16+); erasure coding shed experimental label in 2026 per a secondary source (UNVERIFIED). Lesson: do not depend on it; also a cautionary tale on out-of-tree kernel dependence.
- **lvmcache** (K): front-end to dm-cache (`lvconvert --type cache`), cachevol/cachepool, policies same as dm-cache; also `lvmwritecache`.
- **OpenCAS** (K; Intel Open CAS Framework): modes write-through, write-back, write-around, write-invalidate, pass-through; cleaning policies ALRU, ACP; promotion policies always/nhit; metadata on cache device; supports cache metadata recovery after crash with "dirty" flags; kernel module out of tree but maintained. Provides *per-core* locking and high IOPS.

Common conclusion: all give *block-level cache semantics without ordered write-back*, optimized for latency of repeated hits. Lunix's requirement of an ordered log to S3 means Lunix must implement its own cache. Policy ideas worth borrowing: watermark-based writeback (dm-writecache), sequential-cutoff bypass (bcache), smq-style hotspot promotion for read cache, migration bandwidth throttle (dm-cache), autocommit time as the async-RPO knob.

## 4. Image formats and thin-provisioning

- **qcow2** (K): 2-level L1/L2 tables with cluster size 64 KiB default (512 B-2 MiB), refcount table/blocks for snapshots and COW, L2 cache sized by `l2-cache-size` (rule of thumb: 8 B per cluster -> 1 MiB of L2 cache per 8 GiB of disk at 64 KiB clusters), `cache-clean-interval`, backing files for clone, internal snapshots, subclusters (extended L2, QEMU 5.2+), zlib/zstd compressed clusters (read-mostly, written sequentially), preallocation modes, `discard=unmap` and zero flags per cluster (`QCOW_OFLAG_ZERO`). Lesson: tree-of-tables with cache works; the refcount structure is the source of crash-consistency pain (needs `qemu-img check`); lazy refcounts trade this away. Zero flag per cluster is the model for "all-zero chunks not stored".
- **VHDX** (K): BAT (block allocation table) with 1-32 MiB blocks, **log** for metadata updates (replay on open), differencing disks, chunk ratio; log-based metadata update is the crash-consistency precedent.
- **dm-thin** (K): metadata is a pair of persistent B-trees (device mapping tree keyed by (dev, block) and data space map), copy-on-write via transaction "shadowing" with a **commit** on FLUSH/FUA — crash consistency by atomic superblock swap; snapshots are O(1) (share B-tree subtrees); data block size 64 KiB-1 GiB; the notable issue: metadata space exhaustion (needs monitoring), `pool` out-of-space behaviour is configurable (`error_if_no_space`, default queue IO for 60 s `no_space_timeout`) — **this is the closest existing precedent for Lunix's "block until space or fail EIO/ENOSPC" configuration** (K).
- **ZFS zvol** (K): zvols are ZFS datasets with volblocksize (default 16 KiB, previously 8 KiB), checksummed COW, snapshots and clones O(1), optional inline compression (lz4/zstd), dedup, encryption, send/receive for incremental replication (zfs send over S3 by other tools). Lessons: small volblocksize causes metadata amplification and fragmentation; zvol with sync workloads depends on ZIL/SLOG; `zfs send` as incremental snapshot replication model equals Lunix snapshot diff shipping.

Lesson: metadata with COW B-tree + atomic commit-point at FLUSH (dm-thin) maps well to "metadata log record becomes durable at FLUSH".

## 5. Dedup block stores and chunk repositories

- **VDO / dm-vdo** (V via kernel docs; merged into mainline as `dm-vdo` in Linux 6.9): supports up to 256 TB physical, 4 PB logical; 4 KiB blocks; dedup up to 254:1, compression up to 14:1 (V). **UDS index**: 16-byte block name -> presumed location, records grouped in temporal *chapters*; in-memory *volume index* maps name -> chapter holding newest record, saved only at clean shutdown; default index ~64M records (~256 GB dedup window); **sparse index** extends window 10x without more RAM; index entries are **hints verified by reading the candidate block** (so a false positive is harmless). **Block map**: 5-byte entries (36-bit PBN + 4-bit state) in 812-entry leaf pages across 60 radix trees. **Slab depot**: slabs up to 32 GB with a 1-byte refcount per block and a slab journal; **recovery journal** records intents with flush before and FUA on journal writes. Zoned, one thread per zone, lock-free. Writes ack early (apps must flush/FUA); sub-4K writes need RMW; **compression packing** only helps if >=2 compressed blocks fit in one 4K block; pool of 2048 data_vios bounds in-flight work and recovery; recovery returns to service in degraded mode and rebuilds slabs in background. Numbers from Red Hat docs (K, UNVERIFIED): roughly 1 GB RAM per 1 TB of dense-index physical storage plus a few hundred MB block-map cache; real-world throughput typically 30-50% of raw NVMe for random writes with dedup on (K, UNVERIFIED). Failure modes: index RAM, write latency from synchronous dedup lookup, space reporting confusion (logical vs physical, "out of space" with thin provisioning), growth only (shrink unsupported).
- **ZFS dedup** (K): DDT (dedup table) of ~320 B per unique block in RAM/ARC, on-disk DDT consulted per write; with 128 KiB records and 1 TB data roughly 2.5-5 GB DDT; if DDT does not fit in RAM, write performance collapses (random reads of DDT per write). OpenZFS 2.3 introduced "fast dedup" (log-structured DDT, pruning) to mitigate (K, UNVERIFIED). Lesson: dedup index must be either bounded-RAM (VDO's window) or tiered; or dedup only *within* the S3 upload path (async), not inline.
- **Datto** (K): backup vendor on ZFS; learned dedup is too costly inline; they dedupe at the backup tier.
- **restic** (K): content-defined chunking (Rabin, ~1 MiB avg, 512 KiB-8 MiB), chunks packed into pack files (~4-16 MiB), SHA-256 content address, index files list blob -> pack/offset, encryption AES-256-CTR + Poly1305-AES key derivation (scrypt), compression since 0.14 (zstd); `prune` rewrites packs (the GC cost); lock files in repo (advisory, no conditional write).
- **borg** (K): chunking buzhash, segments, repository index in RAM/local cache (~memory heavy for huge repos), AES-CTR+HMAC or AES-OCB / ChaCha20-Poly1305 (borg2); single-client lock.
- **kopia** (K): content-addressed pack blobs, index blobs (compacted periodically), splitters (fixed or dynamic 2-8 MiB), GCM/ChaCha20, "epoch manager" for index compaction in object storage using only strongly-consistent list+put (no conditional writes) — a good reference for *conditional-write-free* metadata coordination.
- **Longhorn backups** (K): 2 MiB fixed blocks, SHA-hash dedup, incremental by snapshot; simple and shows fixed-size chunking is adequate for VM disks (content-defined helps less for block devices because writes are aligned to fixed sectors/pages; CDC helps mainly for shifted data).

For a block device, fixed-size chunking (aligned, e.g. 16-64 KiB) is almost always better than CDC: guest filesystems align data; CDC saves little and costs CPU and breaks LBA->chunk simplicity. Dedup ratios come from cloned images/OS files, not shifted data.

## 7. The gap for Lunix

1. **Block semantics with object-store durability and portability.** EBS/PD/Azure are single-cloud; Longhorn/Mayastor/DRBD replicate between nodes; Fly volumes are pinned to hosts; Archil/ZeroFS/JuiceFS are filesystems or require a service. A CSI-compatible volume whose durable truth is a set of buckets enables region/cloud moves of pods.
2. **Crash-consistent snapshot in S3 at all times** (prefix consistency) with **bounded async RPO** — only LSVD has the idea and it is research code with no snapshots, dedup, compression, or encryption.
3. **Live multi-backend mirroring** (add Asian bucket, sync, remove USA) — nothing offers this at the block level across vendors. Closest: rbd-mirror, PD async replication, Tigris geo-replication (at the object layer).
4. **Local-FS-only mode with ENOSPC policy and later "attach S3"** — dm-thin's no_space behaviour is the only precedent; nobody does "start local, attach cloud later".
5. **ublk + io_uring in Rust** — NBD/FUSE-based tools are slower; ublk offers zero-copy-ish paths (user-copy / auto buffer reg in recent kernels), so Lunix can approach NVMe-class IOPS on hits.
6. **Dedup + compression + encryption inline at moderate chunk size without VDO's RAM burden**, using hash-addressed chunks and S3-resident index.

## Recommendations for Lunix

### Top 10 design lessons to adopt

1. **Log of sequence-numbered immutable objects + prefix consistency (LSVD).** Define S3 state as `{superblock/manifest, checkpoint(s), log objects 1..N}`; N advances only after all earlier objects are durable. Mountable snapshot = checkpoint + replay of log up to the highest contiguous N. Use 64-bit sequence numbers. Trade-off: a gap (object N+1 missing while N+2 exists) must be ignored by readers and cleaned by the writer; upload objects in parallel but *publish* in order via the manifest pointer.
2. **Separate chunk store from the LBA map.** Chunks: immutable packs (4-64 MiB) of compressed(+encrypted) chunks addressed by hash (restic/kopia pack layout, Longhorn 2 MiB backup blocks show it is viable). Map: log records `(LBA range -> chunk hash / pack,offset,len / ZERO)`. Chunk packs must be durable *before* the log record that references them (Neon's upload-ordering rule). Trade-off: GC must trace references (refcounts or mark-sweep over log+checkpoints).
3. **Fixed-size aligned chunks (e.g. 16 KiB or 64 KiB, configurable per volume, default 64 KiB), not CDC.** Block devices are aligned; use an extent map so large sequential runs coalesce to few records. Trade-off: lower dedup for small chunk misalignment; 4 KiB-granular writes need RMW at chunk level — absorb them in the local write log and only chunk at checkpoint/upload time.
4. **Own the local cache and make it a write-ahead journal (LSVD, dm-writecache autocommit).** Journal on local FS (preallocated file or direct I/O) with checksums; FLUSH/FUA return after journal fsync in async mode; in sync mode after S3 PUT of the log object (or S3 Express/low-latency backend). `autocommit_time`-like knob = RPO. Replay on restart. Never ack before durable at the level promised (ZeroFS NBD FLUSH/FUA discipline, V).
5. **Conditional-write fencing with an epoch in the manifest (SlateDB, ZeroFS, V).** Manifest PUT with `If-Match` etag / `If-None-Match` for first write; embed writer epoch in every log object name or header so a zombie writer's objects are ignored. Provide a fallback for stores without conditional writes (lease object + clock-skew-tolerant TTL, or external lock like ZeroFS' Redis) — mark as "weaker, use at own risk". Kopia shows how to work without CAS (epochs) for index coordination if needed.
6. **Checkpoint objects, incremental and layered (fix LSVD's checkpoint-size weakness, V).** Keep the LBA map as a persistent tree (B-tree / sorted-run LSM) stored as immutable pages in S3, with a small root pointer in the manifest; incremental checkpoint writes only changed pages (dm-thin / ZFS COW style). Fast startup = fetch root + lazy page faults; this directly serves "mount elsewhere with cold cache".
7. **Snapshots = recorded sequence number (+ pinned chunks).** O(1) creation in a log design; clones = new superblock with ancestor pointer at sequence number (LSVD clone linkage, Neon branching, V/K). Consistency groups (PD) for multi-volume pods are a stretch goal.
8. **Lazy hydration with explicit prefetch policy (EBS FSR lesson).** On cold attach: fetch manifest + map root, serve reads by range GET from packs (64 KiB read cache blocks as LSVD, V), background hydrate in map order or by hint (boot/metadata first); expose hydrate progress and "pin/hydrate-all" option. Use pack-level range reads so a miss costs one GET, not a whole pack.
9. **Zero handling as first-class (qcow2 zero flag, VDO).** ZERO extents in the map, no chunk; TRIM/discard and WRITE_ZEROES map to ZERO and enable GC; dm-thin's `error_if_no_space`/queue semantics inspire the configurable ENOSPC behaviour (block vs EIO with timeout).
10. **Test like ZeroFS: pjdfstest, xfstests, fio verify, fault injection / deterministic simulation, Jepsen-style crash tests plus "kill -9 + drop cache device + mount from S3 and fsck" loops.** Crash consistency is the product; automate "mount S3 image at random prefix N and run fsck/db recovery".

Also cheap and valuable: borrow VDO's "index entries are hints" (verify via cryptographic hash makes this unnecessary for hash addressing, but keep a bounded-RAM in-memory bloom/cuckoo filter plus S3-resident full index) and its zone-per-thread sharding of the dedup index/map (shard by hash prefix and LBA range per io_uring thread to avoid locks).

### Top 5 pitfalls to avoid

1. **Unbounded GC and space amplification** (LSVD gc_threshold ~60 => 25% expansion; GC temp file unbounded, V; restic prune rewrites). Make GC rate-limited, resumable, bounded local scratch, cost-aware (PUT/GET/egress billing), and prefer packs with lowest live ratio; keep the in-flight snapshot references accurate. Provide per-backend space and cost reporting.
2. **Index/metadata RAM and read amplification** (ZFS DDT collapse; VDO index RAM; Neon cold start). Do not require the whole dedup index in RAM; use sampling/bloom + S3-resident sorted index, windowed like UDS; bound the LBA-map cache; test at 10+ TB logical.
3. **Lying about durability** (VDO early ack, NFS stable-write semantics in ZeroFS, bcache/writecache cache loss leaving origin inconsistent). Define exactly what FLUSH/FUA/sync-vs-async mean, honour them, document RPO; never expose a cache whose loss breaks the cloud image (the S3 image must be a valid prefix even if local FS is destroyed).
4. **Per-block S3 objects and tiny PUTs** (s3backer). PUT cost and latency dominate; batch into 4-64 MiB objects with timer + size triggers; handle S3 request rate limits and tail latency with hedged GETs and bounded parallelism.
5. **Fixed-at-creation sizes and unbounded checkpoint/sequence structures** (ZeroFS NBD size fixed, V; LSVD 32-bit seq and huge checkpoints, V). Design grow/shrink and format versioning into the manifest from day one (feature flags, superblock version, rolling upgrade across mirrors).

Additional cautions: licensing (ZeroFS AGPL — don't copy code), out-of-tree kernel dependencies (bcachefs lesson, V), and multi-backend mirroring semantics (each backend must independently hold a valid prefix; use the same sequence numbers across mirrors, with a per-backend "durable up to N" watermark; removal of a backend waits for the others to reach N).
