# `lunix-format` freeze checklist

Draft written by M1.A0 (2026-11-12), revised after the independent A0
review. The layouts are specified in
[`docs/reference/on-disk-formats.md`](../../docs/reference/on-disk-formats.md)
and the attach results in
[`docs/reference/attach-matrix.md`](../../docs/reference/attach-matrix.md).
M1.A ticks an item when its type, encoder, decoder and golden files exist
and pass (plan M1.A steps 4 and 5). Only the lead fills in the last line,
after the maintainer's review. After that line is filled, changing any
golden file is a format change and needs the maintainer.

Golden files live in `crates/lunix-format/tests/golden/`, each as `<name>.bin`
plus a `<name>.hex` rendering, generated by the documented command and
compared byte for byte. Files named `a0-*` reproduce a worked example of
on-disk-formats.md §23 byte for byte. `kat-vectors.json` is copied to
`crates/lunix-format/tests/vectors/`.

**Amendment 2026-11-14 (no backward compatibility):** `state/pins` has one
version. A reader accepts only version 2 (136 bytes, `ver` = 2); version 1
(96 bytes, read as "no floor" and upgraded on the next write) is no longer
read, and a version 1 file is rejected like any other bad `ver` or length
(which attach and fsck report as an error, never as "no floor"). The decoder,
the constant for the 96-byte length and `LocalPinsFile::V1_LEN` are gone.
Item 14 goldens: `14-pins.bin` and `14-pins-none.bin` were version 1 files
and are regenerated as version 2 files without a floor (136 bytes, same pins);
`14-pins-v1-read.bin` is deleted; `14-pins-v2.bin` (§23.9) is unchanged. The
version 2 byte layout is unchanged. The same change removes the reading of
short or long checkpoint `stats` slot lists by the engine (an exact
`EngineStats::SLOTS` count is required; that is a code rule, not a byte
change) and edits the text of on-disk-formats.md §20, §24 items 45-46 and
attach-matrix.md Table E (rule E-a, row 120).

Re-signed by: the maintainer (Attila Nagy) on 2026-11-15 (amendment: no backward compatibility, drop pins v1)

**Amendment 2026-11-14** (maintainer decision
of 2026-11-14 after the M12a re-review, finding R1; on-disk-formats.md §5.2
and §5.3). Item 2: bytes 56-63 of the journal record header, reserved and
zero in the signed layout, become `flushed` (u64): the highest `write_seq`
that a completed group flush had made durable on every lane when the record
was appended, always below the record's `write_seq`; 0 when none is known
(the item 2 goldens hold records written before any flush, so they carry 0
there). The reader rejects `flushed >= write_seq`. DELTA regions and the
memfd sink write 0, and the strict DELTA decoder rejects any other value.
Recovery
reports the highest watermark found; a gap at or below it (or a number
found twice) is real loss (what `on_journal_damage = refuse` refuses), a
damaged range with no number missing at or below it holds nothing durable,
and everything above it is crash residue (ADR-4; rule change E1, maintainer
sign-off 2026-11-16 (rule change, no layout change)).

Re-signed by: the maintainer (Attila Nagy) on 2026-11-14 (amendment: journal flushed watermark; merge gated on an independent review and the four-queue kill -9 + refuse cell)

**Amendment 2026-11-14 (b)** (maintainer
decision of 2026-11-14 on finding M2 of the watermark review: close the
unwitnessed window with a witness; on-disk-formats.md §5 intro, §5.1, §5.2,
§5.3 and §5.4). Item 2:

1. Record `kind` 3, `mark`: `len` 0, `lba` 0, `epoch` 0 in phase 1, no data,
   so the record is exactly 64 bytes. `write_seq` is a number of its own
   from the journal's counter and rises within its ring like any record's;
   `flushed` (< `write_seq`) is the watermark the mark witnesses; `gen`,
   `off` and the CRC are those of any journal record. The reader accepts
   kind 3 only with `len` 0 and `lba` 0. A mark changes no block.
2. Mark ring files `journal/m00-<ordinal:08x>.j`: the item 2 file header
   with `lane` 0 and the ordinal of the name, 1 MiB each in phase 1, four
   per journal, one mark per 4 KiB block. Only the flush coordinator writes
   them, one mark at a time, each followed by an `fdatasync`. They are
   reinitialised, reclaimed (once every mark in a file is at or below the
   cut) and recovered like lane files; recovery merges their marks with the
   lanes for `write_seq` contiguity and the watermark, never hands a mark
   to the engine, and reports damage in them under lane id `u16::MAX`. A
   mark file's header is a lane-0 header: only the file name (`m00-` against
   `q00-`) tells the two apart.
3. Marks exist only in the mark ring: DELTA regions and the memfd sink
   never carry kind 3, and the strict DELTA decoder rejects it. Recovery
   treats a record of the wrong kind for its ring (kind 3 in a lane file,
   kind 1 or 2 in a mark file) as damage, never as a record.
4. When a mark is written (§5.3): after a group flush that raised the
   watermark above the last durable cut, unless a later group flush whose
   `upto` is above the counter at that raise completes within the idle
   delay (default 50 ms, configurable): at most one mark per such flush,
   only while no flush is queued, none for a group whose only new number is
   the last mark; after a restart only when records above the floor were
   recovered (once the first lane open made them durable). A mark the full
   ring cannot take is retried as soon as reclaim frees a mark file. The
   last flush stays unwitnessed (medium damage to its records reads as
   crash residue) after a crash within the idle delay, while the ring is
   full until reclaim frees a file, and when marks are off (`mark_idle`
   `None`).
5. New golden: `02-journal-record-mark.bin` (a mark: `write_seq` 9,
   `flushed` 8, `off` 12288). The other item 2 goldens are unchanged.

The wording of the amendment above (2026-11-14) was changed at the same

no backward compatibility while Lunix is in progress); its layout is
unchanged.

Re-signed by: the maintainer (Attila Nagy) on 2026-11-15 (amendment (b): journal mark ring, record kind 3)

**Rule change F1 (2026-11-18, ADR-32).** In `volume.json`, a null
`space.full_timeout_ms` no longer means "wait for ever": it means the
daemon's default full timeout (60 s). No byte of any golden changes; the
row of on-disk-formats.md §21 changes with the implementation (T1).
Maintainer sign-off 2026-11-18 (rule change, no layout change), given with
the acceptance of ADR-32.

**Rule change F2 (2026-11-18, ADR-32 amendment "the cap percentage").**
`volume.json` records how the store's cap was set:
`space.cache_max_percent` (a percentage of the volume size, 100 ..= 10 000)
or `space.cache_max` (an absolute byte count). At most one of them is
non-null; both null means no cap. Both keys are required: a file that lacks
one of the two keys is refused (no default, no migration: Lunix keeps no
backward compatibility while it is in progress). A percentage means
`percent` of the volume size, never below the size plus 2 ×
`commit.dirty_bytes`; it is resolved against the size at every open, on
`lunix space` and on every grow. An absolute cap stays as it is on a grow.
The golden `14-volume.json` gains the `"cache_max_percent": null` line; the
rows of on-disk-formats.md §21 change with it. Maintainer sign-off
2026-11-18 (layout change of `volume.json`), given with the decision "Store %
in volume.json".
